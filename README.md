## 1. 原始定位（硬约束）

改动以下任一条，都需要在 [16-决策记录](docs/16-决策记录.md) 里写明理由。

| 维度 | 约定 |
| --- | --- |
| 游戏类型 | Web 版文字游戏 |
| 游戏主题 | 偶像养成 |
| 游戏定位 | 纯文字、无美术表现，符合上班族办公场景，适配「摸鱼」需求 |
| 游戏特色 | 慢节奏养成、拟真偶像生活、只做贴合上班族节奏的流程（原「养成要素 × 番茄钟」已于 2026-10-29 废弃，见 [16 D-009](docs/16-决策记录.md)） |
| 付费模式 | 初期完全免费 + 玩家自主赞助 |
| 玩家目标 | 玩法 → 提升偶像数值 → 数值转化为收入 → 收入反哺数值 → 循环中获得成就感与养成感 |

> 一句话记住这条循环：**玩得好 → 数字变大 → 赚得更多 → 数字更容易变大。** 所有系统都应该是这条循环上的一环，不是孤立的模块。

## 4. 协作约定

**文档状态**：`🟡 待填` → `🟠 填充中` → `🔵 待评审` → `🟢 已定稿` → `⚫ 已废弃`

1. **文档即需求源。** 实现与文档冲突时，先改文档再改代码；代码里用 `// 见 docs/04-数值与经济.md §2.3` 回指。
2. **一个决定只写一处。** 结论写进对应文档，理由和取舍写进 [16-决策记录](docs/16-决策记录.md)，不要在两处各写一半。
3. **未决问题集中管理。** 聊天里冒出来的、暂时不定的问题，统一落到 [17-待确认问题](docs/17-待确认问题.md)，避免散落在各文档里被遗忘。
4. **术语先定义再使用。** 新名词先进 [15-术语表](docs/15-术语表.md)，之后所有文档用同一个叫法。
5. **每篇文档都有变更记录。** 改动追加一行，不覆盖历史。

### 标记约定（重要）

飞书的勾选框勾上会显示**删除线**，读起来像「作废」而不是「确认」。所以两类东西分开写：

| 类型 | 写法 | 含义 |
| --- | --- | --- |
| 决策未定 | `- 【待填】问题文字` | 还欠内容，搜 `【待填】` 就是待办总表 |
| 决策已定 | `- 【已定】问题 → 结论：xxx（日期）` | 可以直接据此开发，不再回来问 |
| 决策废弃 | `- 【废弃】问题 → 原因：xxx` | 方案作废，同步进 [16-决策记录](docs/16-决策记录.md) |
| 执行类待办 | `- [ ] 要做的事` | 勾上 = 做完了，删除线是正确语义 |

**决策类绝不用勾选框**：删除线只能表达「处理过了」，表达不了「定了什么」，而且结论会丢。

## 8. 快速开始（开发）

```bash
pnpm install        # 首次安装依赖
pnpm test           # core 单测（3 条）
pnpm dev                              # 客户端 http://127.0.0.1:5273
pnpm --filter @idollife/server start  # API    http://127.0.0.1:8787
pnpm build          # 构建
```

仓库结构：

```
packages/core      纯函数规则：结算、随机、类型（客户端与服务器共用）
packages/client    Vite + React 界面
packages/server    API：/health、/v1/sync（用同一份 core 重放）
```

> 铁律：`packages/core` 里不能出现 `Date.now()`、`Math.random()`、DOM、localStorage。
> 时间与随机都由参数传入，这样才能「客户端算、服务器重放校验」。
### 后端存储

默认用本地 JSON（`packages/server/.data/runs.json`），零配置。

接 Supabase：

1. 在 Supabase SQL Editor 执行 `packages/server/db/idollife-runs.sql`（建 `public.idollife_runs` 表）
2. 把 service_role key 填进 `packages/server/.env`（该文件不进 git）
3. 重启 server，`/health` 里会显示 `store: supabase`
### 登录与同步

- 客户端读 `packages/client/.env` 的 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`（anon key 可公开）
- 不登录也能玩，但**只有登录后才会同步到服务器**
- 服务端用 `Authorization: Bearer <access_token>` 验身份，局归 `user_id` 所有（别人的局返回 403）

自检脚本：`packages/server/scripts/probe-auth.mjs`、`probe-ownership.mjs`
### 部署（Vercel，两个项目）

**1. API 项目**
- Root Directory: `packages/server`
- Framework: Other
- 环境变量：`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`CORS_ORIGINS`（客户端域名，逗号分隔）
- 路由前缀是 `/api`（例：`/api/health`、`/api/v1/sync`）

**2. 客户端项目**
- Root Directory: `packages/client`
- Framework: Vite，输出 `dist`
- 环境变量：`VITE_SUPABASE_URL`、`VITE_SUPABASE_ANON_KEY`、`VITE_API_BASE=https://<API 域名>/api`

**顺序**：先部署 API 拿到域名 → 配客户端环境变量并部署 → 把客户端域名填进 API 的 `CORS_ORIGINS` → 重新部署 API。

本地开发不需要这些：`pnpm dev` 会把 `/api` 代理到 `127.0.0.1:8787`。
