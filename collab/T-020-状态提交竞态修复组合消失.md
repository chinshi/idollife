# T-020 状态提交竞态：handler 产出新状态未同步 runRef，被时钟 tick 覆盖

## 现象（用户报告）

玩家组建组合成功（toast「组合创建好了。」，日志随后出现「完成任务『组个团』(+500)」），
切几次页签回到「组合」页 → 显示「还没有组合，先创建一个。」，组合凭空消失。

## 根因分析（策划已定位，dsh 负责修复与全面排查）

1. 游戏时钟 tick（App.tsx rAF 循环，约 497-499 行）以 `runRef.current` 为结算底稿：
   `settle(runRef.current, ...)` → `runRef.current = result.state` → `setRun(result.state)`。
2. `runRef` 的同步只依赖 passive effect（约 424 行 `useEffect(() => { runRef.current = run; }, [run])`）。
   **passive effect 在 paint 之后才执行**，而 rAF 回调在 paint 之前执行——
   handler 里 `setRun(newState)` 之后、effect 同步之前，下一次 tick 读到的 `runRef.current`
   仍是旧状态，settle 出来的 `result.state`（旧底稿）会把 newState 整个覆盖掉。
3. `confirmCreateParty`（约 1224 行）正是这样：只 `setRun(state)` + `pushWholeState(state)`，
   没有同步 `runRef.current`。时钟运行中创建组合 → 下一 tick 用旧状态结算 → 组合被抹掉。
4. `applyIdolName`（约 1159 行）在 T-016 已修过同类问题（手动 `runRef.current = next`），
   但其余全部 handler 都还带着这个雷。受影响面包括但不限于：
   `confirmCreateParty`、`doReward`、`doAccept`、`doMeet`、`doKick`、
   买/用道具、装备、抉择 choose、事件 decide、占卜等所有「产出新 RunState 后 setRun」的调用点。
   这也解释了 T-013 bug 2（任务状态被清空）可能复发：doReward/doAccept 同样有此竞态。

## 修复要求

1. 新增统一提交函数（示意）：
   ```ts
   function commitRun(next: RunState) {
     runRef.current = next;
     setRun(next);
   }
   ```
2. **审计 App.tsx 全部 `setRun(` 调用点**（包括条件分支里的），凡是「基于旧状态计算产出新状态」的，
   一律改为 `commitRun(...)`，并删除各处冗余的手动 `runRef.current = ...`（tick、endBatch、
   applyIdolName 保留等价写法即可，口径统一后以 commitRun 为准，避免双写混乱）。
   - 纯设置初始/重置类（useState 初始值、doRestart 的 `setRun(initialRun)`、云端恢复 367 行等）
     也建议走 commitRun，保持口径唯一；367 行的云端恢复发生在时钟可能已启动后，**必须**同步 runRef。
3. handler 内计算新状态的底稿一律取 `runRef.current`，不再用闭包 `run`（避免陈旧渲染闭包），
   例如 `createParty(runRef.current, partyName)`、`claimTaskReward(runRef.current, taskId)`。
   仅展示用途的读取可保留 `run`。
4. `pushWholeState` 的实参同步改为提交后的状态（commitRun 的入参），保持现有行为不变。
5. 不改 packages/core；不改服务端。

## 回执区（dsh 填写）

- 实现说明：

  1. **统一提交口**：`App.tsx` 新增
     ```ts
     function commitRun(next: RunState) {
       runRef.current = next;

     ```
