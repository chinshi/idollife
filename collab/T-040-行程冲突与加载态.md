# T-040 行程与运行的冲突 + 加载态

- 状态：`done`（用户直派，策划本人实现，未派 dsh）
- 提出：2026-11-05 00:05（用户 5 条报障）
- 更新：2026-11-05 00:40

## 1. 用户原话

1. 安排行程的【清空行程】，将正在执行的行动也清空了，导致执行出问题
2. 修改行程时，会被执行中的行程覆盖，导致无法修改行程
3. 属性的晋级按钮和悬浮提示偏移过远，将晋级按钮放大
4. 将属性中的占卜入口去掉
5. 所有提交/领取任务/事件交互等需要提交服务端且要等服务端回复的按钮，都要加加载中的等待状态

## 2. 根因

### 2.1 第 1 条：清空后留下「僵尸 running」

`clearPlan` 只保留 `s.done`，把未完成的**全部**清掉。清空后：

- 服务端 `schedule` 没有未完成项 → `nextStopAt` 恒为 `null`
- 客户端调度器 `shouldFireAdvance` 永不触发 → 不再有任何 `advance`
- 但 `clock.status` 仍是 `running`，`wallAnchor` 一直在走
- 玩家再点推进 → `POST /v1/start` 返回 409 `no_schedule`

于是「时间不动、推进点不动」，玩家理解为「执行出问题」。

另有一个更隐蔽的后果：这段空转的墙钟时间被记在 `wallAnchor` 上，之后一旦加回行程，
`maxTargetAt` 会把空转时长折算成游戏时间，一次性补算出一大批条目。

### 2.2 第 2 条：本地编辑被服务端旧副本覆盖

两处叠加：

1. `putSchedule()` 里先 `serverAdvance` 对齐，再 `applyServerState(aligned.data)` ——
   后者无条件 `scheduleRef.current = data.schedule`，把玩家刚改的行程整份盖成服务端旧版，
   然后又把这份旧版提交上去。**改动从未生效过。**
2. 安排行程弹窗开着时，后台 100ms 调度的 `advance` 仍在跑，每次回包都 `applyServerState`，
   玩家的每一次增删都被下一个 tick 冲掉。

### 2.3 第 3 条：tooltip 用估算高度定位

`openTip` 里 `const H = 140`，而提示框实际内容只有 70–90px 高，
`top = r.top - H - gap` 于是把提示框推到按钮上方 140px 处。

### 2.4 第 5 条：动作是 fire-and-forget

`doReward` / `doBookShow` 等一律 `void pushFresh(...)`，不 await、不置忙，
点击到回包之间界面毫无变化；连点还会拿旧 `revision` 撞 409 后重放，数值跳变。

## 3. 改法

| # | 改动 | 位置 |
|---|---|---|
| 1 | 新增 `isExecuting(item, at)`（右开区间 `startAt <= at < endAt` 且未 done）；`clearPlan` 保留 `done ∪ isExecuting` 并提示保留了几条；`removeItem` 命中正在执行的直接拒绝 | `core/plan.ts`、`App.tsx` |
| 1 | `PUT /v1/state` 提交后若排程无未完成项且 clock 为 running → 收敛成 `paused`（`wallAnchor` 归零） | `server/app.ts` |
| 2 | `putSchedule` 先抓本地快照 → 对齐只取「哪些已 done」和「现在到哪一刻」→ `reconcileSchedule(local, doneIds, at)` 合并后提交，内容以本地为准 | `core/plan.ts`、`App.tsx` |
| 2 | 编辑弹窗打开期间（`showActions`）调度 effect 直接 return，不跑自动推进；弹窗加提示「编辑期间界面暂停刷新」 | `App.tsx`、`Modals.tsx` |
| 3 | `top` 改用 `r.top - gap`，向上展开由 CSS `translateY(-100%)` 顶上去；按钮 11px/2px10px → 12px/4px12px + `min-height:24px` | `StageAdvanceButton.tsx`、`styles.css` |
| 4 | 侧栏属性页底部的「占卜」按钮删除（占卜仍从主菜单「占卜」页进） | `SidePanel.tsx` |
| 5 | 新增 `busyKey` + `runBusy(key, task)`：飞中互斥、被点的那个显示加载文案；事件抉择改为**回包后才关弹窗** | `App.tsx`、`api.ts`、各面板 |

`reconcileSchedule` 的规则（按优先级）：
1. `done` —— 服务端已确认执行完，保留
2. `endAt > at` —— 正在执行或还没开始，保留
3. 其余未完成且 `endAt <= at` —— 已错过执行窗口（settle 会 `item.startAt < cursor` 跳过），移除

## 4. 守卫

| 编号 | 断言 |
|---|---|
| `plan-reconcile` ×7 | `isExecuting` 右开区间 / done 不算在跑；`reconcileSchedule` 保留正在执行、丢掉过期、补 done、不改入参 |
| G16 | `PUT` 提交空排程 → `clock.status === 'paused'`、`wallAnchor === 0`、`nextStopAt === null` |
| G17 | `PUT` 仍有未完成排程 → 保持 `running`，`nextStopAt` 正确（不能误停） |
| G18 | paused 时 `PUT` 不会把钟拉起来 |

证红记录：
- `isExecuting` 改闭区间 → `expected true to be false`
- `reconcileSchedule` 去掉 filter → `expected ['past','running','future'] to deeply equal ['running','future']`
- 去掉服务端 paused 收敛 → `expected 'running' to be 'paused'`

## 5. 真实服务端验收（`.tmpdev/verify-t040-clearplan.ts`）

| 场景 | 结果 |
|---|---|
| A 清空成空排程（挂着 30 分钟） | `clock=paused`、`nextStopAt=null` → 不再空转 |
| B 保留正在执行的（1 条） | `clock=running`，再 advance → `stepped=1`、跑完 10 分钟、转 paused |
| C 清空 2 小时后重新加行程 | `clock=paused`，`stepped=0` —— **没有补算那 2 小时** |

## 6. 没做的

- `doKick` / `doInvite` / `doSwitchParty` 仍是纯本地 `commitRun`，不落库（既存问题），
  所以没给它们加载态 —— 它们本来就不等服务端。
- 编辑期间不暂停服务端时钟，只停界面刷新；关弹窗时由 `putSchedule` 一次对齐。
