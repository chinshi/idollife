## 0. 三条退货（每条都有我这边跑出来的证据）

### R1【致命】在线推进的定时器永远不触发

**位置**：`packages/client/src/App.tsx` 里「到下一个停点才向服务端要结果」那个 `useEffect`（约 540–568 行）

```ts
useEffect(() => {
  if (!running || !clock || clock.status !== 'running') return;
  const next = nextPendingItem(schedule)?.endAt;
  if (!next || gameNow < next || advancingRef.current) return;
  const timer = window.setTimeout(() => { /* advance */ }, 200);
  return () => window.clearTimeout(timer);
}, [running, clock, gameNow, schedule, revision, runId]);   // ← gameNow 在 deps 里
```

**为什么必然不触发**：`gameNow` 由另一个 100ms `setInterval` 每帧改写 → 本 effect 每 100ms 重跑一次 → cleanup 清掉上一个 200ms 的 timer → 200ms 永远等不到。

**我跑的证据**（复刻 React effect 语义：deps 变化即 cleanup 再执行）：

```
100ms interval 连续 setGameNow，停点已越过：
  3 秒内 renders=27  fired=0
```

**后果**：玩家点「开始推进」→ 服务端进入 running → 进度条在走 → **永远不会结算下一条**。只有刷新页面（走 `GET` + `advance { targetAt:null }`）才会跳一次。这正好复现用户报了很久的「点了推进没反应」。

**修法**（任选，但必须满足「到点必发一次」）：

- 把判定合并进那个 100ms interval：同一次 tick 里既 `setGameNow` 也判断 `gameNow >= next` 并发 `advance`；
- 或者 deps 去掉 `gameNow`，在 interval 里用 ref 读取当前 `gameNow`；
- 定时器无论怎么排，**不许把「每 100ms 都会变的值」放进取 200ms 以上超时的 effect deps**。

**必须新增守卫**：把「该不该推进」抽成纯函数，例如

```ts
export function shouldFireAdvance(input: {
  clock: ClockState | null;
  schedule: ScheduleItem[];
  serverNow: number;
  timeScale?: number;
}): { fire: boolean; targetAt: number | null };
```

单测至少 5 条：未到点 `fire=false` / 到点 `fire=true` 且 `targetAt === endAt` / `paused` 时 `false` / 无未完成项 `false` / 已越过停点很久仍 `true`（不能因为「过了太多」就放弃）。

### R2【高危】挂机中一旦跳过过期项，就永久停死

**位置**：`packages/server/src/app.ts` 的 `POST /v1/advance`

```ts
const keepRunning = result.stoppedReason === 'time' || result.stoppedReason === null;
```

`docs/30 §6` 明确要求：**`'exhausted'` 但排程仍有未完成项 → running**（这是 T-026 就踩过的坑，旧 `catchUp` 里有这个分支，本单重写服务端时丢了）。

**我跑的证据**（一条 `startAt` 已过期、`done=false` 的行程，`clock` 为 running）：

```
[R2] status = paused | stoppedReason = exhausted | stepped = 0
[R2] 期望 running（docs/30 §6：exhausted 但排程仍有未完成项）
```

**后果**：挂机过程中只要有一条因故没被执行（过期 / 空档 / 跨天对齐），服务端就把 status 打成 `paused`，客户端停止唤醒，玩家回来看到「时间停了」。这跟「离线挂机是核心玩法」直接冲突。

**修法**：

```ts
const keepRunning =
  result.stoppedReason === 'time' ||
  result.stoppedReason === null ||
  result.executed.length >= maxSteps ||
  (result.stoppedReason === 'exhausted' && schedule.some((s) => !s.done));
```

（`schedule` 用 `markDone` 之后的那份。）

**必须新增守卫**：`G11 过期未完成项 → advance 后仍为 running`。先证红（当前代码应红）。

### R3【致命】运行中任何「改状态」都必然 409，且重试还是 409

**位置**：`packages/client/src/App.tsx#pushWholeState`

```ts
async function pushWholeState(next: RunState, overrideRunId?: string) {
  const aligned = await serverAdvance(id, revision, null, token);  // ① 对齐，服务端 at 前进了
  let expected = revision;
  if (aligned.kind === 'ok') { applyServerState(aligned.data); expected = aligned.data.revision; }
  const res = await putState(id, expected, { run: next, ... });    // ② 但 next 是「对齐前」算出来的
  ...
  else if (res.kind === 'conflict' || res.kind === 'stale_clock') {
    const retry = await putState(id, res.data?.revision ?? expected, { run: next, ... });  // ③ 同一个 next，还是旧 at
  }
}
```

`next` 由调用方基于 `runRef.current`（对齐前的 run）算好传进来，`at` 是旧值。服务端 `PUT` 校验 `body.run.at !== rec.run.at` → `stale_clock`。第 ③ 步重试只更新了 `expectedRevision`，`run.at` 没变 → 再 409 → 函数静默返回。

**我跑的证据**（真实 `createApp` + file store）：

```
[R3] advance → at 前进 20 游戏分钟 | stepped = 2 | rev = 2
[R3] 旧 at 的 PUT → 409 stale_clock
[R3] 重试（同一个旧 run）→ 409 stale_clock
[R3] rebase 到最新 at 的 PUT → 200 ok
```

**后果**：**挂机运行中**送礼 / 创建组合 / 邀请 / 改名 / 存行程 / 抉择——全部失败，且界面不报错。T-036 时代那个「改了没生效、被服务端旧副本还原」的毛病，会以「改完直接被拒」的新形态回来。

**修法**（卡面 §5.5 的原始口径就是这个，实现时被压扁了）：

```ts
// 接受变换函数，而不是算好的 run
async function pushWholeState(change: (base: RunState) => RunState, overrideRunId?: string) {
  const aligned = await serverAdvance(id, revision, null, token);
  const base = aligned.kind === 'ok' ? aligned.data.run : runRef.current;   // ← 用对齐后的 run 当 base
  const next = change(base);
  const res = await putState(id, aligned.kind === 'ok' ? aligned.data.revision : revision, {
    run: next, schedule: scheduleRef.current, seed,
  }, token);
  ...
}
```

20 个调用点全部改成 `pushWholeState((base) => ({ ...base, money: base.money - cost }))` 这种形式。**不许**在调用前就把 `next` 算好传进来。

**必须新增守卫**：`G12 变更 rebase 到对齐后的 run`——断言提交的 `run.at` 等于服务端对齐后的 `at`，而不是调用前的 `at`。可以抽成纯函数 `rebaseChange(base, change)` 单测，或用假 fetch 断言请求体。
