# T-011 · 失败可见化：过期不再凭空消失

- 状态：`done`（2026-11-02 16:31 验收通过）
- 认领时间：2026-11-02 16:29
- 完成时间：2026-11-02 16:30
- 发起：机枢 ｜ 日期：2026-11-02
- 优先级：P1
- 依据：docs/25 §2.5 A（软失败口径）、T-007（`expired` / `expiredDay`）、T-010（倒计时）

## 背景（为什么做）

用户验收 T-010 时问「有没有加失败状态和可视面板」，实测后发现**两个都漏了**，而且漏得比预想严重。

用真实数据（`task-vocal-20`，`deadlineDays: 3`）逐行动跑出的实测链路：

```
+8  行动: active  剩 1 次
+9  行动: active  due          ← 显示「期限已到」
+10 行动: 结算前 expired → 结算后 hidden   ← 任务在这里消失
+11 行动: hidden
日志:   通告「声音先立住」超时未完成。
```

根因是 T-007 的「同日冷却」用了 `hidden`：

```ts
if (expired === today) return 'hidden'; // 当日冷却：不再出现
```

而界面渲染的是结算**后**的 state，于是：

- `TaskStatus = 'expired'` 变成了「一帧状态」，玩家永远看不到
- `TaskPanel` 里的「已过期」状态标签、按钮「已过期」文案、「已过期」分区 → **全是死代码**（分区永远空）
- T-010 刚加的红色「已超时」也没机会显示（它只在 `status === 'expired'` 时渲染）

玩家体验是**任务做着做着凭空消失**，只剩日志里一行小字——这比不做失败状态更糟，玩家会当成 bug。

另外全仓 `grep -n "reputation|信誉|penalty|fail"` → **0 命中**：没有失败次数记录、没有信誉、没有惩罚，连 docs 里说的「先留接口」也没留。

## 设计口径（已与产品确认 2026-11-02）

**软失败：只记录，不惩罚。**

- 不扣钱、不扣粉、不掉心情、不消耗 `times`
- 错过当天任务**留在面板上**，灰标「已错过」+ 提示「明日起重新可领」
- 次日恢复可领（`expiredDay < today` 的现有逻辑，不改）
- 累计错过次数**记下来并展示**，但不产生任何数值后果

冷却的语义从「不可见」改成「**不可操作**」——既给反馈，又照样不能在同一天反复领了过期、过期了再领。

## 需求描述

### 1. `expired` 当天可见（`packages/core/src/tasks.ts` 的 `statusOf()`）

```ts
// 改前：当日冷却直接隐藏，玩家看不到任何失败反馈
if (expired === today) return 'hidden';
// 改后：当日冷却 = 仍可见但不可操作
if (expired === today) return 'expired';
```

上层 `if (expired !== null && today > expired) return claimable/locked` 保持不动（次日恢复可领）。

### 2. `expireTasks()` 必须幂等（**关键，不改会刷屏**）

现在 `expireTasks()` 只看 `statusOf() === 'expired'` 就写 flag + 加日志。第 1 条改完后，过期当天**每次结算都会命中这个分支**，结果就是每做一个行动写一条「通告『X』超时未完成」——日志刷屏，`expiredCount` 也会被灌爆。

加前置守卫（写在 loop 里、写 flag 之前）：

```ts
const today = gameDay(next.at);
if (expiredDay(next, task.id) === today) continue; // 今天已经结算过这次超时
```

要求：**同一游戏日内连跑 N 次 `expireTasks()`，日志只增加 1 条，`expiredCount` 只 +1**（测试要钉死这条）。

### 3. 累计错过次数

- 新 flag：`task:<id>:expiredCount`（number，缺省 0）
- 在 `expireTasks()` 写 `expiredDay` 的同一处 `+1`（同一次超时只加一次）
- 新导出 `expiredTimes(state, taskId): number`，风格对齐现有 `doneTimes()`
- 旧存档无此 flag → 按 0 读，**不做迁移**

### 4. 面板（`packages/client/src/components/TaskPanel.tsx`）

| 位置 | 改动 |
| --- | --- |
| 状态标签 `expired` | 「已过期」→**「已错过」** |
| 按钮 `expired` 分支 | 「已过期」→**「已错过」**（保持 disabled） |
| 倒计时位（`expired` 行） | 文案 **`明日起重新可领`**，class 保持 `due`（红色不该再用了，改成中性灰：见第 5 条） |
| `.task-req` | 新增一项：`expiredTimes > 0` 时显示 `<em>错过</em>N 次`（放在「时限」之后、「奖励」之前） |
| 「全部」页签分区 | `expired` 分区标题改 **「已错过」**，标题后面拼**当天**错过数：`已错过 · 今日 N 单`（N = `expiredDay === 今天` 的条数，N 为 0 时只写「已错过」）；分区位置放在「进行中」之后、「已完成」之前（现在就在那儿，别动顺序） |
| 「领取任务」页签 | 保持包含 `expired`（现在已包含，验收时确认它还看得见） |

倒计时的 `due` 红色**只留给「期限已到」那一刻**（`active && due`）。`expired` 行改用中性灰，理由：错过是既成事实，红色是警告色，用在事后只会制造焦虑，且和「期限已到」的警告抢注意力。

### 5. 样式（`packages/client/src/styles.css`）

- 新增 `.task-deadline.missed`：`color: var(--muted);`（替代 `due` 用在 expired 行）
- 现有 `.task-deadline.due`（红 `#c0392b`）**保留**，只给 `active && due`（「期限已到」）用
- 若分区标题需要弱化数字，用既有 `var(--muted)`，不加新类也行

### 6. 测试（`packages/core/tests/tasks-expire-visible.test.ts` 新建）

至少 6 条，数字追 `DAY_MS` / `ACTION_MS` / `DAILY_SLOTS`：

1. 过期当刻（`at > deadlineAt`、未结算）→ `taskStatus === 'expired'`（**不再是 hidden**）
2. 过期当天连续推进 3 次行动（每次 `expireTasks`）→ 状态始终 `expired`，**日志只多 1 条**，`expiredTimes === 1`
3. 次日（`at + DAY_MS`，跨过 `expiredDay`）→ 状态回到 `claimable`（若 `acceptCondition` 满足）
4. `expireTasks` 幂等：同一 state 连跑 3 次 → `expiredTimes` 仍为 1、日志仍只 1 条
5. 第二次真的再错过 → `expiredTimes === 2`（隔日重新领取、再次超时）
6. 无 `deadlineDays` 的任务跑 `expireTasks` → 状态不变、`expiredTimes === 0`、日志不增
7. 旧存档（flags 里没有 `expiredCount`）→ `expiredTimes()` 返回 0，不抛错

## 验收记录（机枢填，2026-11-02 16:31）

- 结论：**通过**。实现与口径一致，并额外修掉一个 T-007 遗留的真 bug。
- 我独立复跑：core `23 文件 108 条`、client `1 条`、`check:data ✓`。
- 我用真实数据（`task-vocal-20`，3 天 = 9 行动）独立复现，结果：
  ```
  领取: active 剩 9 次
  +9  行动: active   due      ← 期限已到（橙）
  +10 行动: expired  错过1次 超时日志1条   ← 不再消失
  +11 行动: expired  错过1次 超时日志1条   ← 同日内不重复记账
  同 state 连跑 3 次 expireTasks → 错过1次、日志1条（幂等 ✓）
  次日: claimable（重新可领 ✓）
  二次超时: expired 累计错过2次 日志2条 ✓
  ```
- 未决 1 的裁定：**接受**。`expired >= gameDay(acceptedAt)` 的守卫是对的，而且它修的是 T-007 的真 bug——旧逻辑下「上一次领取」留下的 `expiredDay` 会污染「这次领取」的判定，隔日重领后再超时会被直接判成 `claimable`，等于**第二次起永远不算超时**。这条我核过四种时序（同日超时 / 隔日超时 / 隔日重领再超时 / 同日内跨日），没有漏。
- 未决 2 的裁定：**接受**。旧档 `expiredCount` 从 0 起算，历史错过不补记——试玩期没有真实玩家存档，补记没有意义。
- 补充确认：`activeTasks()` / `taskBadgeCount()` 都不含 `expired`，所以信息区简报和菜单角标不会被「已错过」污染（已核 App.tsx）。
- 遗留（不在本卡范围）：信息区任务简报（时间轴右侧那 6 条）仍只显示 `brief` 文字，不显示剩余行动数——真正的紧迫感入口在那里，但它属于「简报改版」，另开卡。
