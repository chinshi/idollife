## 背景

用户反馈原话：

> 启停逻辑整体不太对，要重新设计，启停逻辑都要服务端保存和校验，不然仅保存在本地，和服务端的数据对不上。

这不是"补一个接口"能解决的。已定位五个漏洞，全部有代码依据：

### 漏洞 1：服务端存的是"上一批"，不是最新一批

`packages/client/src/App.tsx:1107`（`endBatch` 末尾）：

```ts
void pushSync(batch.prevRun, batch.prevSchedule, batch.from, result.state.at, result);
//              ^^^^^^^^^^^^^ 批次开始前的 run
```

`prevRun` 是批次**开始前**的状态，而客户端本地已经 `commitRun(result.state)` 推进到批次结果。
送到服务端的 `run.at` 因此永远落后一批 —— 换设备 / 清缓存从云端恢复，就退回一批之前。

### 漏洞 2：暂停是本地私事

`packages/client/src/state/clock.ts` 的 `paused` 只写 `localStorage`（`idollife:clock:v2`）。
服务端没有"暂停"这个概念。换设备后 `bootResume`（`App.tsx:1429`）读到 `isClockPaused() === false`，
一看到有未完成排程就自动 `advance()` 跑起来。这是"数据对不上"最直观的来源。

### 漏洞 3：服务端不做任何时间校验

`packages/server/src/app.ts:117`，`/v1/sync` 的全部校验只有一条：

```ts
if (existing && existing.run.at > run.at) { /* 409 stale */ }
```

钱、属性、任务奖励、时间跨度全盘接受。客户端把 `run.at` 改成一年后，服务端照收。
`docs/09-技术选型.md §4.2` 写的"服务器时钟是时间唯一权威""速率限制""离线重放"，
`docs/12-时间系统.md §3` 写的"以服务器时钟重放排程""改系统时间无效"——**目前一行都没实现**。

### 漏洞 4：离线流逝只在客户端算，且依赖本地时钟

`App.tsx:266-295` 在启动时读 `localStorage` 的 `{t, w}`，用 `Date.now() - w` 补离线时间，
上限 6 小时，且 `speed` 来自本地存储。改系统时间可以直接刷进度。

### 漏洞 5：多端无互斥

同一账号两台设备同时开着，后一次 `putRun` 直接覆盖前一台，没有任何提示或仲裁。

### 附带的交互语义问题

`doStop()`（`App.tsx:1164`）当前语义是"当前这条行动作废，其余行程保留"，文案也这么写
（`已停止：当前这条行动作废，其余行程保留。`）。玩家点一次暂停，正在做的事就白费了。
正常产品里暂停应该是**停在这里，回来接着做**。

## 一、core：新建 `packages/core/src/clock.ts`

### 1.1 模型

```ts
export type ClockStatus = 'idle' | 'running' | 'paused';

export interface ClockState {
  status: ClockStatus;
  /** 已结算到的游戏时间（权威水位线）；不变量：=== 对应 RunState.at */
  gameAt: number;
  /** status='running' 时有效：服务端墙钟锚点（Date.now() 毫秒）；其余状态为 0 */
  wallAnchor: number;
  /** 倍速档位；只接受 ALLOWED_SPEEDS */
  speed: number;
  /** 推进权持有者；用于「后到者接管」识别旧端 */
  sessionId: string | null;
  /** 最近一次状态变更的墙钟时间 */
  updatedAt: number;
}

export const ALLOWED_SPEEDS = [1, 2, 4, 8] as const;
```

`createClock(gameAt, overrides?)`：默认 `{ status:'idle', gameAt, wallAnchor:0, speed:1, sessionId:null, updatedAt:0 }`。

### 1.2 `catchUp()` —— 本单最核心的纯函数

```ts
export interface CatchUpOptions {
  /** 周目结束点（T0 + RUN_LENGTH_MS），到点停 */
  endAt?: number;
  /** 单次最多结算的行动条数，默认 200，防死循环 */
  maxSteps?: number;
}

export interface CatchUpResult {
  state: RunState;
  schedule: ScheduleItem[];
  clock: ClockState;
  /** 本次补算执行掉的行动 id（按执行顺序） */
  executed: string[];
  stoppedReason: StopReason;
  /** 本次实际推进的游戏毫秒（state.at - 入参 clock.gameAt） */
  advanced: number;
}

export function catchUp(
  run: RunState,
  schedule: ScheduleItem[],
  clock: ClockState,
  nowWall: number,
  seed: string,
  opts?: CatchUpOptions,
): CatchUpResult;
```

**铁律**：不读 `Date.now()`（`nowWall` 由参数传入）、不读 `Math.random()`、不碰 DOM/存储。

**算法**（按这个写，别自创）：

```
1. clock.status !== 'running'  → 原样返回，advanced=0、executed=[]
2. target = clock.gameAt + max(0, nowWall - clock.wallAnchor) * clock.speed
3. result = settle(run, schedule, clock.gameAt, target, seed, { endAt })
   —— settle 内部已按 item.endAt <= to 判定，只用跑完整的行动；
      遇到 item.endAt > to 会返回 stoppedReason='time' 并停在最后完成点。
      gap（下一条 startAt 远大于当前 at）不需要额外 heal：settle 会跳过空档直接把 at 推到该条 endAt。
4. schedule = markDone(schedule, result.executed)
      —— markDone 从 client 的 markExecuted（App.tsx:1080）迁移进 core：
         打 done 标记，且只保留最近 60 条已完成的（老的不再回传，防数组无限涨）
5. 若 result.executed.length >= maxSteps → 视为「还没算完」，clock 保持 running（下次继续）
6. clock.gameAt = result.state.at
7. 若 stoppedReason === 'time'（时间用完但排程还有）
      → status 保持 'running'
      → wallAnchor = nowWall - (target - clock.gameAt) / clock.speed
        （把未消费的零头留在锚点里，否则每次刷新都会白丢最多一条行动的时长）
   否则（event / stamina / money / stopped / ending / exhausted）
      → status = 'idle'，wallAnchor = 0
8. advanced = clock.gameAt - 入参 clock.gameAt
```

**边界要求**：

| 场景 | 期望 |
| --- | --- |
| `status='paused'` / `'idle'` | 完全不推进，`advanced=0` |
| `nowWall < wallAnchor`（时钟回拨） | `elapsed` 取 0，不推进 |
| 排程耗尽 | `stoppedReason='exhausted'`，`status='idle'` |
| 命中 A 级事件 | `stoppedReason='event'`，`state.pendingEvent` 有值，`status='idle'` |
| 体力/钱不足 | `stoppedReason='stamina'|'money'`，`status='idle'` |
| 到达 `endAt` | `stoppedReason='ending'`，`status='idle'` |
| 时间落在某条行动中间 | 该条不执行，`gameAt` 停在上一条结束点，`status` 保持 `running` |

**确定性要求**：同一输入下，"服务端一次算完"与"客户端拆成多次算"结果必须一致
（settle 的 rng 按 `${seed}:action:${item.id}` 派生，D-010 已保证；本单要加测试守住）。

### 1.3 导出

`clock.ts` 从 `packages/core/src/index.ts` 导出 `ClockState` / `ClockStatus` / `ALLOWED_SPEEDS` / `createClock` / `catchUp` / `CatchUpResult` / `markDone`。

### 2.1 存储字段


> 这一句由策划转给用户执行；dsh 不要尝试跑 DDL，也不要因为列不存在就把功能降级。

### 2.3 统一入口 `withClock(runId)`

新建 `packages/server/src/clock-service.ts`，所有读写路径先过它：

```ts
/** 读一局并做懒补算：running 就 catchUp 到 now，有推进则落库 */
export async function loadAndCatchUp(runId: string, now: number): Promise<{
  rec: RunRecord;
  offline: { from: number; to: number; executed: string[]; stoppedReason: StopReason } | null;
}>;
```

- `store.getRun` → 缺 clock 补默认 → `catchUp(...)` → `advanced > 0` 则 `putRun`（revision+1）
- `offline` 非空表示"这次读取补算了离线进度"，返回给客户端做提示

### 2.4 接口

#### `POST /v1/clock/start`

```ts
// body
{ runId: string; sessionId: string; speed?: number }
// 200
{ clock: ClockState; run: RunState; schedule: ScheduleItem[]; revision: number;
  offline: {...} | null; serverTime: number }
```

处理顺序：
1. `loadAndCatchUp`（离线进度先补上）
2. 校验 → 失败返回 409 + `reason`：
   - `no_schedule`：没有未完成排程
   - `pending_event`：`run.pendingEvent` 非空
   - 速度不在 `ALLOWED_SPEEDS` → 400 `bad_speed`
3. 写入：`status='running'`、`wallAnchor=now`、`speed=speed??1`、`sessionId=body.sessionId`、`updatedAt=now`
4. `revision+1` 落库

**后到者接管**：`sessionId` 不同时**直接覆盖**（这就是用户选的口径）。旧端下次任何请求会收到 `409 taken_over`，见 §2.5。

#### `POST /v1/clock/pause`

```ts
{ runId: string; sessionId: string }
// 200 同上结构
```

1. `loadAndCatchUp`（把已经流逝的部分结算掉）
2. 若 `clock.sessionId !== sessionId` → `409 taken_over`
3. `status='paused'`、`wallAnchor=0`、`updatedAt=now`、落库

> 幂等：已经是 paused/idle 时直接返回当前状态，不报错。

#### `POST /v1/clock/session`（可选但建议）

用于客户端打开页面时确认自己是不是当前持有者，避免每次都靠一次失败的 `sync` 才发现被接管：

```ts
{ runId: string; sessionId: string }
// 200 { clock, run, schedule, revision, offline, holder: boolean }
```

`holder = clock.sessionId === sessionId || clock.sessionId === null`。
不修改任何状态（若 holder 为 true 且 clock.sessionId 为 null 则顺手写入 sessionId）。

### 2.5 `/v1/sync` 改造为"结算上报"

**保留路径与请求体主体**，但语义与校验全部重写。

```ts
// body
{
  runId: string;
  sessionId: string;
  run: RunState;          // 客户端结算后的状态（不是 prevRun！）
  schedule: ScheduleItem[];
  to: number;             // 客户端声称到达的游戏时间
  seed: string;
}
```

校验顺序：

1. `loadAndCatchUp(runId, now)` 拿到权威 `rec`、`clock`
2. `clock.sessionId !== sessionId` → `409 taken_over`（带权威状态）
3. `run.at !== to` → `400 bad_to`（客户端自相矛盾）
4. `to < clock.gameAt` → `409 stale`（不得倒流，返回权威状态）
5. **水位线校验**（核心）：

```ts
const allowed = clock.gameAt + Math.max(0, now - clock.wallAnchor) * clock.speed + 1000; // 1 游戏秒容差
if (to > allowed) return c.json({ error: 'too_fast', reason: 'too_fast', ...权威状态 }, 409);
```

6. **服务端重放比对**（核心）：

```ts
const replay = catchUp(
  rec.run, body.schedule,        // 以客户端带来的排程为准（排程是玩家操作，不防）
  { ...clock, status: 'running', wallAnchor: 0 },  // 借用 catchUp，等价于 settle(from=gameAt,to=to)
  /* nowWall */ clock.gameAt + (to - clock.gameAt),   // 让 target 正好等于 to
  seed, { endAt: RUN_LENGTH_MS },
);
```

更直接的做法：直接调 `settle(rec.run, body.schedule, clock.gameAt, to, seed, { endAt })`，
再 `markDone`。**不必绕 catchUp** —— 但 catchUp 已经处理了 markDone，二选一，别写两套。

比对关键字段（**容差不做**，必须完全一致）：

```
state.at / stamina / money / mood / satiety / health / stats.* / axes.* /
fans 总数 / inventory 条目数 / pendingEvent / log.length
```

- 一致 → 接受：`clock.gameAt = to`、`clock.wallAnchor = now`（重置锚点防累积误差）、
  `rec.run = body.run`、`rec.schedule = body.schedule`、`revision+1`、落库、返回 200
- 不一致 → `409 mismatch`，**以服务端重放结果为准**写入并返回；客户端收到后校准（见 §3.4）

> 为什么要重放而不是直接用客户端提交的 run：这是"服务端校验"的实质。
> 只校验时间的话，客户端改钱/改属性照样能过。

**白名单例外：跨空档前移（必须实现，否则必误判）**

客户端 tick 在 `App.tsx:556` 有"跨空档对齐"：下一条行程还没开始时会 `commitRun({...run, at: next.startAt})`——
**只把 `at` 前移，不执行任何行动**。此时上报的 `run.at` 会大于服务端重放得到的 `state.at`（重放因 `endAt > to`
一条都没执行），若按"完全一致"判定就会误报 `mismatch`。

处理规则：重放后若 `replay.state.at < to`，检查 `body.schedule` 里是否存在一条未完成项满足
`item.startAt === to`，且 `replay.executed.length === 0`（一个行动都没跑过）——
满足则以客户端带来的 `at` 为准接受（仅时间前移，数值不做任何改动），否则按 `mismatch` 处理。

> 同时要求客户端：`commitRun(healed)`（跨空档前移）之后立刻上报一次，不要等到下一条行动跑完。

7. 响应体保留 `{ runId, revision, accepted, stoppedReason, state, clock, serverTime }`
   —— 客户端现有解析逻辑要同步加 `clock`。

### 2.6 `/v1/choice` 也要过时钟

当前 `pushChoice` 直接覆盖 `run`，同样能偷时间。加一条：

- 走 `loadAndCatchUp`
- `body.run.at > clock.gameAt + 1000` → `409 too_fast`

（`choice` 不推进时间，`run.at` 应等于 `clock.gameAt`。）

### 2.7 `GET /v1/runs/latest` / `GET /v1/runs/:id`

都改为走 `loadAndCatchUp`，返回体补 `clock` 与 `offline`。

## 三、client：播放器化

### 3.1 删除本地暂停判定

- `packages/client/src/state/clock.ts`：整文件删除，或降级为**纯显示缓存**
  （只存 `gameNow` 插值位置给首屏用，不参与任何"是否推进"的判断）。
  推荐直接删，避免又变成第二真相。
- `App.tsx:266-295` 的 `bootClockRef` 离线补算（含 6 小时上限）**整段删除**——
  离线补算改由服务端 `catchUp` 负责。
- `App.tsx:1429` 的 `bootResume` 改为读服务端 `clock.status`：
  - `running` → `setRunning(true)`，本地接着播放
  - `idle` / `paused` → 不自动推进，提示"上次停在XXX，点继续"
- `packages/client/tests/clock.test.ts`（T-024 为 `paused` 写的 4 条单测）随 `clock.ts` 一并处理：
  文件删除则测试删除；保留显示缓存则改测缓存读写。**不要留着测已删除行为的用例**，并在回执里说明取舍。

### 3.2 启停改走接口

| 原函数 | 改为 |
| --- | --- |
| `advance()` | 先 `POST /v1/clock/start`，成功后 `setRunning(true)`；失败按 `reason` 给文案 |
| `doStop()` | 先 `POST /v1/clock/pause`，成功后 `setRunning(false)` |

**暂停语义改为"停在这里"**（用户已确认的变更）：

- 旧文案：`已停止：当前这条行动作废，其余行程保留。`
- 新文案：`已暂停：停在这里，回来接着走。`
- 行为：不再作废当前行动。`pause` 时服务端 `catchUp` 会停在最后一条**完整执行**的行动结束点，
  未完成的那条保持未完成、`startAt` 不变，回来继续跑完。

### 3.3 sessionId

- 客户端启动时生成一次：`crypto.randomUUID()`，存 `sessionStorage`（关标签页即失效）
- 所有 `start` / `pause` / `sync` / `choice` 请求带上

### 3.4 上报时机

现在只在 `endBatch` 上报，且传的是 `prevRun`。改为：

1. **每完成一条行动就上报**（`App.tsx` rAF tick 里 `result.executed.length > 0` 处）
   —— 请求体 `run` 用 `result.state`，`schedule` 用 `markExecuted` 后的结果，`to = result.state.at`
2. `endBatch` 再补一次收尾上报（此时通常无新增，幂等）
3. 上报走 fire-and-forget，**不得阻塞 tick**；失败进内存队列，下次成功时合并补报
4. 收到 `409 taken_over` → `setRunning(false)` + 顶部只读横幅「另一台设备接手了这局」
   + 按钮「在此设备继续」（再调一次 `start` 抢回）
5. 收到 `409 mismatch` / `too_fast` / `stale` → 以响应里的权威 `run`/`schedule`/`clock` 校准本地，
   提示「已按云端进度校准」

### 3.5 离线摘要

`start` / `latest` / `session` 响应里的 `offline` 非空时，`setNotice`：

> 你不在的这段时间，行程又走了 N 条。（停在：事件 / 体力不足 / 排程跑完）

N = `offline.executed.length`。二期再做详细回放。

### 3.6 清理

- `pushSync` 的签名去掉 `prevRun/prevSchedule/from`，改为传 `result.state` 与当前排程
- `App.tsx:1575` 那处 `writeClock(...paused:false)` 一并清掉
- `speed` 仍可由 UI 调，但改档要**先 `pause` 再 `start(speed)`**（改档会重算 `wallAnchor`）
