## 先回答用户的两个疑问（已用线上数据核实，不是推测）

**状态存进服务器了吗？存了。** 云端那一局（`run-mvz0cvih-1p3bl6`，rev 61）的 `clock` 字段是：

```json
{ "status": "idle", "gameAt": 1767285120000, "wallAnchor": 0, "speed": 1,
  "sessionId": "30dd8d25-…", "updatedAt": 1793710588742 }
```

`sessionId` 有值、`updatedAt` 正好是刷新那一刻 —— 说明 start 确实写过库，暂停/推进也都在写。

**页面打开去取状态了吗？去了。** `App.tsx:428` 开屏一定会调 `fetchClockSession`，
`clock.status === 'running'` 时才 `setRunning(true)`（`App.tsx:444`）。

所以问题是：**取回来的 status 已经不是 running 了**。下面两条根因都指向这个。

---

## 根因 A：起播 5 秒 = 4 次跨境串行往返（已实测）

`POST /v1/clock/start` 的服务端路径是四段串行网络调用：

| 步骤 | 代码 | 实测耗时 |
| --- | --- | --- |
| 1. 校验 token | `auth.ts` → `sb.auth.getUser(token)` | 1.07–1.11s |
| 2. 读存档 | `clock-service.ts` → `store.getRun()` | 1.16–1.20s |
| 3. 回写（补算有变更）| `loadAndCatchUp` 里 `scheduleOverride !== undefined` 必触发 `putRun()` | 1.2s |
| 4. 写时钟 | `app.ts:171` `saveClock()` 又一次 `putRun()` | 1.2s |

四次相加 ≈ **4.7s**，与用户说的「5 秒左右」对得上。实测方法：直接对 Supabase REST 打表，三次读分别 1.19 / 1.20 / 1.16s，`auth/v1/user` 1.07 / 1.11s。

第 3 步是纯浪费：`start` 先把「补算结果」写一次库，紧接着第 4 步又把同一行写一次。
第 1 步也可以省：同一个 token 在几分钟内重复校验没有意义。

## 根因 B：`catchUp` 把「暂时没活干」当成「跑完了」，一读就打成 idle

`packages/core/src/clock.ts:112-124`：

```ts
if (result.stoppedReason === 'time') { status = 'running'; … }
else { status = 'idle'; wallAnchor = 0; }   // event / stamina / money / stopped / ending / exhausted 一律 idle
```

而 `settle` 的 `exhausted` 语义是「这一窗口内没有可结算的行动就退出」（`settle.ts:245`
`if (!stoppedReason) stoppedReason = 'exhausted'`）。它包含两种完全不同的情况：

1. **真的跑完了**（排程全 done）→ 该 idle，没问题。
2. **只是空档 / 时间不够一条行动**（下一条 `startAt` 还在后面，或本次窗口太短）→ **不该 idle**。

再看 `loadAndCatchUp`：它挂在**所有**读路径上（session / start / pause / sync / choice），
并且只要 `status` 变化就 `putRun` 落库。于是：

- 客户端刚 start（running，`wallAnchor=now`，`gameAt=run.at`）；
- 下一次 sync / 刷新开屏 → `catchUp` 的窗口只覆盖「现在」到「下一条开始前」，`settle` 返回 `exhausted`；
- **status 被改成 idle 并写进库**；
- 客户端 `App.tsx:444` 读回 idle → 不自动播放 → 界面回到「待执行」。

这就是「明明在跑，刷新就回待执行」。线上那条记录 `status: idle` + `wallAnchor: 0` 正是这么写进去的。

**顺带暴露的反向漏洞**：客户端本地循环因 exhausted 停下来时（`App.tsx:629` `setRunning(false)`），
只 `reportProgress` 报了一次状态，**从不把 clock 落成 idle/paused**。服务端会一直以为在 running，
关页面后按 running 补算 —— 迟早把排程一次性烧掉。

## 必须做的五件事

### P0-1 `catchUp`：只有「真的跑完」才降级（core）

`packages/core/src/clock.ts`，把 else 分支拆开：

- `stoppedReason === 'exhausted'` 且排程里**还有未完成项**（`nextSchedule.some(s => !s.done)`）
  → **保持 running**，`wallAnchor = nowWall - Math.max(0, target - gameAt) / speed`
  （与 `time` 分支同口径，把没消费的零头留在锚点里）。
- `stoppedReason === 'exhausted'` 且排程**全 done** → idle。
- `event / ending / stamina / money / stopped` → idle（现状不变）。

单测（`packages/core/tests/clock.test.ts` 追加）：

- running + 下一条在 5 分钟后 → `catchUp` 后 `status === 'running'`，`gameAt` 不变；
- running + 排程全 done → `status === 'idle'`；
- 空档跨过后继续 `catchUp` 到足够时间 → 行动正常执行（验证铁律：一次算完 == 拆成多次算）。

### P0-2 压缩往返：start 从 4 跳降到 2 跳（server）

- `packages/server/src/auth.ts`：加进程内 token → user 缓存（`Map<string, {user, exp}>`，TTL 5 分钟，
  只缓存成功结果；401 时删除对应项）。省掉 1 跳。
- `packages/server/src/app.ts` `/v1/clock/start`：合并两次 `putRun`。
  做法给两个选项，选简单可靠的一个：
  - 给 `loadAndCatchUp` 加 `dryRun?: boolean`（只算不写），start 拿到计算结果后
    **连同新 clock 一次 `putRun`**；或
  - start 不再传 `scheduleOverride` 触发写库，改为自己组装「排程 + 时钟」一次写。
- 目标：`start` 只剩「读一次 + 写一次」= 约 2.4s；配合 P0-3 用户感知为 0。

### P0-3 客户端乐观启动：点击即进入运行态（client）

`App.tsx` `advance()`：

- 点击后**立刻** `setRunning(true)` + 建 `batchRef` + `setSyncStatus('syncing')`，
  不要等服务端往返；时间轴从本地 `run.at` 起播。
- 服务端返回 `ok` → 用权威 `state/clock/revision` 校正（`applyAuthoritative`）。
- 返回 `no_schedule` / `pending_event` / `taken_over` / `unauthorized` / `error`
  → **回滚**：`setRunning(false)`、清 `batchRef`、`applyAuthoritative`（若有）并给对应提示。
- 不许出现「本地已经在跑，但服务端说没排程」的静默分叉：回滚必须有可见提示。

### P0-4 自然结束要收尾，别让服务端一直 running（client）

`App.tsx:625-632`，本地循环因 `stoppedReason !== 'time'` 停下时：

- 除了现有 `reportProgress`，再调一次 `pauseClock()`（或新增轻量 `POST /v1/clock/idle`），
  把服务端 clock 落成 `paused`/`idle`，`wallAnchor=0`。
- 失败可忽略（下次开屏的 session 会纠正），但**不能**因此回滚用户已完成的进度。

### P0-5 开屏不许静默停在「待执行」（client）

`App.tsx:427-455` 开屏会话确认：

- 请求发出到返回这段时间，`syncStatus` 置 `syncing`，界面明确显示「正在同步云端时钟…」，
  不要先渲染成「待执行」再无声跳变。
- `fetchClockSession` 失败（`kind === 'error'`）→ **重试一次**（间隔 1s）；
  仍失败 → 显示「云端时钟读取失败，已切换为只读，点这里重试」，并给一个手动重试入口，
  不允许什么都不提示。
- `taken_over` → 沿用现有只读横幅。

1. **P0-1 测试前提有偏差**：`settle` 对「下一条在 5 分钟后」返回的是 `stoppedReason==='time'`（`item.endAt > to`），不是 `exhausted`；原逻辑在 `time` 分支已经是 running。真正会被误打成 idle 的 `exhausted` 出现在「有未完成项但 `startAt < cursor` 被跳过」这类空档/错位。因此测试 1 用「已过点未完成项」覆盖新分支；「5 分钟后」由「空档跨过后继续」用例覆盖（先 time、后正常执行）。
