## 用户原话

> 行动的属性要求要在行动前进行判断而不是在执行完成后判断。

补充澄清（同轮答复）：

> 目前的现状是：当前体力为 0，但是可以点击推进，等倒计时结束后，告知体力不足停止了行程，该没有完成。应该调整为点击开始推进时就做属性判定，能不能开始推进

> 遇到不满足时：停在当前条并提示

## 一、根因（已核对，别改错地方）

| 位置 | 现状 |
|---|---|
| `App.tsx#advance()`（约 1264 行） | 只拦两种：`pending` 为空、`run.pendingEvent` 存在。**完全不判第一条能不能跑** |
| `core/settle.ts` | 次数/体力/钱三条判定在里面（`remainingTimes` / `preview.stamina` / `preview.money`），命中就 `stoppedReason` 并 `break` |
| 结果 | 玩家点击 → 时钟上钟、倒计时开始走 → tick 里 settle 才发现跑不了 → 停。**白等一整格** |

settle 里那三条判定本身是**在行动之前**执行的（命中时 `state.at` 不变、`executed` 为空），逻辑没错；错的是**入口没提前问同一句话**。

---

## 二、口径（实现不得偏离）

### 1. 判定逻辑抽成 core 单一真相

新增 `packages/core/src/preflight.ts`（纯函数，禁随机 / 时间 / DOM）：

```ts
export type PreflightReason = 'ok' | 'stamina' | 'money' | 'times';

export interface PreflightResult {
  ok: boolean;
  reason: PreflightReason;
  /** 给玩家看的一句话（ok 时为空串） */
  text: string;
  /** 需要多少 / 现在多少（ok 时为 undefined；次数用尽时 need=0） */
  need?: number;
  have?: number;
}

/** 判这一条现在能不能跑：次数 → 体力 → 钱（顺序与 settle 一致） */
export function preflightAction(state: RunState, actionId: string): PreflightResult;
```

- 必须复用现有派生：`remainingTimes()`、`previewAction()`。**不许另写一套体力/钱公式**。
- `settle()` 内部那三条判定改成调用它，`stoppedReason` 映射保持原样：
  `times → 'stopped'`、`stamina → 'stamina'`、`money → 'money'`。
  **现有 settle 测试一条都不许改**，必须原样通过。

### 2. 文案固定（客户端与 settle 提示共用，禁止两套措辞）

| reason | text |
|---|---|
| `stamina` | `体力不够：这条要 20 点，你现在 5。先安排恢复，或删掉这条。` |
| `money` | `钱不够：这条要 ¥60，你现在 ¥20。` |
| `times` | `这条本周的次数用完了（每周 1 次）。` |

（数字由 `need/have` 填；`timesScope` 为 `day/week/run` 时分别说「今天/本周/本局」。）

### 3. `advance()` 入口拦截（核心改动）

`advance()` 在现有的「空排程 / pendingEvent」检查之后、**任何副作用之前**插入：

```ts
const first = scheduleRef.current.filter(s => !s.done).sort((a,b) => a.startAt - b.startAt)[0];
const pf = first ? preflightAction(runRef.current, first.actionId) : null;
if (pf && !pf.ok) {
  setNotice(pf.text);
  dbg('推进被拦截 reason=' + pf.reason);
  return;            // 不 setRunning、不写本地 clock、不发 start 事件
}
```

**必须零副作用**：不能 `setRunning(true)` 再回滚，不能入队后再取消，不能写 `localStorage`。
拦截时要像「没排程」那条分支一样，点了立刻就出提示（同帧，无 await）。

### 4. tick 侧不改行为，但文案要同源

中途第 1 条跑完后体力掉到不够第 2 条时，settle 会立刻停（`state.at` 不前进、不消耗时间），这条**已经是对的**。
只要求：`endBatch` / `lastStop` 显示的停止原因，`stamina`/`money` 两档改成用 `preflightAction` 的 text，**不再用现在 `STOP_TEXT` 里的「体力不足，行程停下来了」**（两套措辞会让玩家以为两种情况不一样）。
`exhausted` / `stopped` / `event` / `ending` 四档文案保持不变。

### 5. 明确禁令：不要把 `displayCondition` 纳入执行前判定

`actions.json` 里 `recover/sick-bed` 的条件是 `stamina < 25`——**反向条件**。体力回上来后它变假，如果拿 `displayCondition` 当执行门槛，玩家会有一条永远跑不了的行程。
`displayCondition` 的语义**只是列表显隐**，本次不动。属性门槛（total ≥ 60 那类）是否要做成硬拦截，等策划另行定案。
