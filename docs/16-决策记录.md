# 16 · 决策记录（ADR）

> 状态：🟡 待填 ｜ 负责人：陈曦 ｜ 更新：2026-10-27

## 为什么需要这个

半年后你会忘记「为什么当初不用 React」「为什么番茄钟不做成强制」。写下决策，是为了**避免重复讨论同一个问题**，也为了知道当时放弃了什么。

## 记录规则

1. 一个决策一条，编号 `D-001` 起，只增不改
2. 结论改了不删旧条目，新开一条并标注「取代 D-xxx」
3. 状态只有三种：`提议` / `已采纳` / `已废弃`

## 模板

```markdown
### D-00X · 标题

- 日期：YYYY-MM-DD
- 状态：提议 / 已采纳 / 已废弃（若取代，写：取代 D-00Y）
- 涉及文档：

**背景**：什么问题需要决定？

**选项**：
1. A —— 优点 / 缺点
2. B —— 优点 / 缺点

**决定**：选了什么。

**理由**：为什么。

**代价**：接受了什么坏处。

**回滚条件**：什么情况下应该重新考虑。
```

### D-007 · 异步联机（新增）

- 状态：**已采纳** ｜ 涉及：02 / 13 / 18
- 决定：联机 = 异步组团演出。玩家在窗口期自选报名并配置，截止后锁定，到点由服务器撮合（NPC 补位）并统一演算
- 理由：实时联机与摸鱼场景冲突；异步能提供「周末回来看结果」的留存钩子
- 代价：必须做后端与账号；结算必须可复算
- 回滚条件：大演出参与率长期低于阈值时，降级为纯单机

### D-009 · 废弃番茄钟（2026-10-29，取代 D-002）

- 状态：**已采纳** ｜ 涉及：01 / 02 / 12 / 03 / 08 / 13 / 14 / 15 / 18
- 决定：删除番茄钟整套设计（25 分钟时长、长短休、连击、轮次奖励）。时间改为「**行动驱动 + 排程自动流逝**」。
- 保留：**自动流程**。玩家排好计划即可离开，碎片化摸鱼需求仍然成立；去掉的只是「固定时长专注」场景。
- 理由：番茄钟要求玩家在场专注，而本作核心机制是「提前规划 → 自动流逝 → 无排程则静止」，两者互斥。保留它会让两套时间观互相打架。
- 代价：
  - 失去唯一「别人没有」的机制，差异化改为**内容与节奏**
  - 偏离需求源头《IF核心和主题》中「养成要素和番茄钟结合」的原始设定
  - [01 §2.2](01-产品定位与目标用户.md) 的差异点论证需要重写
- 回滚条件：若以后想恢复「专注」要素，**不要再嵌回时间轴**，而应做成独立的可选小工具（例如完成专注换一次额外行动），不驱动主线时间。

### D-010 · 结算确定性：随机流按行动派生（2026-11-02）

- 状态：**已采纳** ｜ 涉及：10 / 11 / 12 / 18
- 背景：T-001 盘点发现 `settle` 每次调用重置随机种子，客户端增量结算与服务端一次重放序列不同，联机可复算（D-007/D-008 的前提）不成立。
- 决定：随机流按「行动实例」派生种子（全局 seed + 行动唯一序号），同一行动无论一次算还是分多次算，结果必须一致。以测试钉死：「同一排程，一次结算 vs 分三次结算，属性/金钱/粉丝/日志完全一致」。
- 理由：这是联机重放的地基；不修，后续演出撮合与结算全部白做。
- 代价：需要给每个行动分配稳定序号，排程数据结构微调。
- 回滚条件：派生种子方案若导致存档兼容断裂且迁移成本过高，回到「批次种子 + 禁止分批」的次优解。

### D-011 · repeat 任务语义（2026-11-02）

- 状态：**已采纳** ｜ 涉及：25 / 22
- 决定：repeat 任务完成后，**下一个游戏日开始时重置为可再领**；`times` 表示「累计可完成次数」，达上限后任务转为长期完成态，不再重置。
- 理由：给日常登录一个稳定节奏锚点；立即重置会让玩家在一天内无限刷，违背慢节奏定位。
- 代价：需要记录「上次完成的游戏日」。
- 回滚条件：若玩家测试反映「每天有可做的事太少」，改为完成即重置但每日次数上限 1。

### D-014 · 时间尺度基准：1 行动 = 10 游戏分钟（2026-11-02）

- 状态：**已采纳** ｜ 涉及：12 / 13 / 17(Q21) / 25、`balance.actionMinutes`、`packages/client/src/App.tsx`
- 决定：
  1. **唯一时间刻度是「行动」，1 行动 = 10 游戏分钟**。这是正式口径，不再有"阶段不同、行动跨度不同"的时间解释。
  2. **一天 = `dailySlots`(3) 个行动 = 30 游戏分钟**（`content.ts` 的 `DAY_MS = DAILY_SLOTS * ACTION_MINUTES`）。日历按行动走，不按 24 小时走。
  3. **当前配置值 `actionMinutes = 10` 是正确的**（2026-11-02 随 `all.xlsx` 更新落地）。历史上出现过的 `1` 是**测试临时值**，不是设计值。
  4. **客户端「时钟倍速」功能（`App.tsx` 的 `speed`，持久化在 `localStorage['idollife:speed']`）属测试便利设施**，不是玩法。上线前必须移除，或改为仅在开发模式可见（见 13 P3 上线清单）。
- 理由：行动是玩家唯一的决策单位，玩家感知的是「我这一步干了什么、花了多久」，不是真实时钟。把行动跨度与阶段绑死会让同一套内容数值在不同阶段体感相反，无法排数值。
- 代价：`docs/12 §2` 原来按阶段划分行动跨度的表作废，已改写；24 条任务时限的数值只能在 10 分钟/行动 的口径下排。
- 回滚条件：若上线后实测「一天 3 个行动」节奏过快/过慢，调 `dailySlots`（1 天几个行动），**不要调 `actionMinutes`** —— 后者是尺度基准，动它会同时改掉所有时限、演出时长与房租周期的语义。
- 遗留影响：`tasks` 表的「时限(小时)」列在不换算的情况下语义别扭（1 游戏小时 = 2 游戏日），填数值前需决定是否改用「天」为单位。

### D-015 · 废弃「上班摸鱼」设定，定位改为沉浸式养成；美术反需求解除（2026-11-03）

- 状态：**已采纳** ｜ 涉及：01 / 02 / 08 / 12 / README
- 决定：
  1. **废弃「上班摸鱼场景」整套设定**：目标人群不再是「工位偷玩的上班族」，画像不再按办公场景（工位 / 会议 / 通勤）划分。

### D-016 · 时钟权威归服务端（2026-11-03，部分恢复 D-008）

- 状态：**已采纳** ｜ 涉及：09 / 10 / 11 / 12 / 16 / 18、`collab/T-025`
- 决定：
  1. **时钟状态由服务端持有**：`ClockState = { status, gameAt, wallAnchor, speed, sessionId }`。客户端只能发三种意图——`start` / `pause` / `settle`（一条行动的结算上报），不能直接写时间。
  2. **`gameAt` 是唯一进度口径**（权威水位线）。客户端界面上的时钟是 `gameAt + (now − wallAnchor) × speed` 的插值，仅用于播放。
  3. **离线流逝由服务端懒补算**：玩家下次任何请求时，服务端按墙钟 `elapsed` 重放排程（`catchUp`），排程耗尽 / 撞事件 / 资源见底即停。不依赖本地时钟，不设"最多补几小时"的人为上限（天然的界是排程长度）。
  4. **结算校验走水位线 + 重放比对**：客户端上报的 `to` 不得超过 `gameAt + 真实流逝 × speed + 容差`；服务端用同一份 `settle` 重放并比对关键数值，不一致以服务端为准。只校验时间不校验数值，等于没校验。
  5. **多端后到者接管**：新会话 `start` 直接覆盖 `sessionId`，旧端收到 `taken_over` 转只读，可显式抢回。
  6. **暂停语义改为「停在这里」**：不再作废当前行动。暂停点 = 最后一条**完整执行**的行动结束时间，未完成的那条回来后继续跑完。
- 理由：
  - T-024 把「玩家主动暂停」写进 `localStorage` 后，问题暴露：**时间的权威在浏览器里**，服务端只是一个 KV。换设备、清缓存、多端同开都各自为政，"两端数据对不上"是必然而非偶然。
  - `docs/12 §3` 早就写了"以服务器时钟重放排程""改系统时间无效"，`docs/09 §4.2` 也写了速率限制与离线重放，但**一行都没实现**——文档与实际脱节比没有文档更危险。
  - D-008 把服务端权威"降级"的理由是「无榜单 → 不需要防改档」。这个理由只覆盖**防作弊**，不覆盖**数据一致性**。为了一致性必须让服务端持有时间，与是否做榜单无关。
- 代价：服务端要能跑 `settle` 重放（`settle` 已是纯函数、随机按行动 id 派生，D-010 已铺好路）；Supabase 表加一列 `clock`；客户端启停全部改走接口，`localStorage` 的 `paused` 判定删除。
- 回滚条件：若"逐次重放比对"导致 `mismatch` 高频误伤（正常操作被反复打回），退回次优解——**服务端只持有状态机 + 水位线校验，不做数值重放比对**；再不行才退回纯本地时钟，但必须保留"暂停态上云"这一条（它是用户体感最痛的部分）。
- 不做（一期之外）：离线战报 UI、单日行动上限与属性跳变检测等防作弊体系、逐条实时上报的节流优化。
