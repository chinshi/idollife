## 为什么需要这个

半年后你会忘记「为什么当初不用 React」「为什么番茄钟不做成强制」。写下决策，是为了**避免重复讨论同一个问题**，也为了知道当时放弃了什么。

## 记录规则

1. 一个决策一条，编号 `D-001` 起，只增不改
2. 结论改了不删旧条目，新开一条并标注「取代 D-xxx」
3. 状态只有三种：`提议` / `已采纳` / `已废弃`

## 模板

```markdown
### D-00X · 标题

- 日期：YYYY-MM-DD
- 状态：提议 / 已采纳 / 已废弃（若取代，写：取代 D-00Y）
- 涉及文档：

**背景**：什么问题需要决定？

**选项**：
1. A —— 优点 / 缺点
2. B —— 优点 / 缺点

**决定**：选了什么。

**理由**：为什么。

**代价**：接受了什么坏处。

**回滚条件**：什么情况下应该重新考虑。
```

### D-007 · 异步联机（新增）

- 状态：**已采纳** ｜ 涉及：02 / 13 / 18
- 决定：联机 = 异步组团演出。玩家在窗口期自选报名并配置，截止后锁定，到点由服务器撮合（NPC 补位）并统一演算
- 理由：实时联机与摸鱼场景冲突；异步能提供「周末回来看结果」的留存钩子
- 代价：必须做后端与账号；结算必须可复算
- 回滚条件：大演出参与率长期低于阈值时，降级为纯单机

### D-008 · 服务端权威（新增）

- 状态：**已采纳** ｜ 涉及：09 / 10 / 11 / 18
- 决定：属性与结算由服务端持有；客户端只做显示与预估
- 理由：无榜单时不需要服务端权威；若未来加排名，才必须防改档
- 代价：MVP 的结算函数从一开始就要纯函数化、可复算、随机走种子
- 回滚条件：若最终不做排名，可退回纯本地

### D-009 · 废弃番茄钟（2026-10-29，取代 D-002）

- 状态：**已采纳** ｜ 涉及：01 / 02 / 12 / 03 / 08 / 13 / 14 / 15 / 18
- 决定：删除番茄钟整套设计（25 分钟时长、长短休、连击、轮次奖励）。时间改为「**行动驱动 + 排程自动流逝**」。
- 保留：**自动流程**。玩家排好计划即可离开，碎片化摸鱼需求仍然成立；去掉的只是「固定时长专注」场景。
- 理由：番茄钟要求玩家在场专注，而本作核心机制是「提前规划 → 自动流逝 → 无排程则静止」，两者互斥。保留它会让两套时间观互相打架。
- 代价：
  - 失去唯一「别人没有」的机制，差异化改为**内容与节奏**
  - 偏离需求源头《IF核心和主题》中「养成要素和番茄钟结合」的原始设定
  - [01 §2.2](01-产品定位与目标用户.md) 的差异点论证需要重写
- 回滚条件：若以后想恢复「专注」要素，**不要再嵌回时间轴**，而应做成独立的可选小工具（例如完成专注换一次额外行动），不驱动主线时间。
