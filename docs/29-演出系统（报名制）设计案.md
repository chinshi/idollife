## 0. 一句话

演出从「排程里的一个行动」变成「一张挂在日历上的通告」：提前 60 天贴出海报 → 玩家报名抢顺位（或报名个人通告）→ 当天自动占住排程并结算。

## 1. 旧 → 新 对照（要先删掉的东西）

## 2. 时间口径（必须先对齐，否则数值全错）

| 量 | 值 | 来源 |
|---|---|---|
| 1 行动 | 10 游戏分钟 | `balance.actionMinutes` |
| 1 游戏天 | 3 行动 = 30 游戏分钟 | `balance.dailySlots` |
| timeScale | 20（1 真实秒 = 20 游戏秒） | `balance.timeScale`（T-028） |
| **1 游戏天** | **90 真实秒 = 1.5 真实分钟**（1×） | 推导 |
| 60 游戏天 | 90 真实分钟（1×）／11.3 分钟（8×） | 报名窗口 |
| 15 游戏天 | 22.5 真实分钟（1×） | 违约金分界 |
| 7 游戏天 | 10.5 真实分钟（1×） | 报名截止 |
| 一周目 | 730 天 ≈ 18.3 真实小时（1×） | `balance.runDays` |

**结论**：60 天报名窗口在 1× 下约 1.5 小时，玩家一个晚上会跨过好几次截止。因此海报**不能一次性铺满**，必须按周滚动生成（§5.1），否则列表会瞬间堆出十几场。

## 3. 类型与报名单位

| 类型 | 字段值 | 报名单位 | 顺位数 | 结算方式 | 时段 |
|---|---|---|---|---|---|
| 拼盘演出 | `circuit` | 组合 | 4～7（按城市） | 五模块拆分 | 周末（超一线另有周中） |
| OM 舞台 | `one-man` | 组合 | 1 | 全领，不分拆 | 周末，后期 |

- OM 是后期玩法：出现条件要求 `已出道 && 组合名气 ≥ 3000`。

## 4. 配置表 `shows`（T-033 重写：一场一行）

主键：`演出 id`（一行一场）。**不再有城市列**，也**不再一个顺位一行**——中间顺位由首末两行线性插值，导入时展开。

### 4.1 为什么改

T-032 版本按「城市 × 顺位」写：同样一场演出要在三线/二线/一线/超一线各写一遍，加一场演出要写 4 遍 + 每个顺位一行。城市越多、顺位越多，配置量是乘法。

T-033 反转：**演出池只有一份，城市只决定「能看到哪些」**。一场演出 = 一行。

### 4.3 插值规则（导入时执行，`scripts/content-import.mjs`）

```
t = (slot - 1) / (slotCount - 1)      // slotCount = 1 时 t = 0
值(slot) = round(首值 + (末值 - 首值) × t)
```

- 顺位名派生，不写表：`slotCount=1` → 主位；否则 1=开场、`slotCount`=压轴、`slotCount-1`=次压轴、其余=中坚。
- `npcWeight` 派生：`1 + 0.2 × (slot - 1)`（开场最先被 NPC 占满，见 §5.5）。
- 导入后 `shows.json` 仍是「一顺位一行」（203 行），但**这是构建产物，人不碰**。

## 5. 城市、刷新与阵容

### 5.1 城市**不决定演出池，只决定看的范围**（T-033 拍板）

`run.city`（0=超一线 / 1=一线 / 2=二线 / 3=三线），开局三线，第一周内可改（搬迁功能等 P2）。

城市的三个作用全部在 `cities` sheet 里，代码不许写死：

| 城市 | 周末场 | 周中场 | 顺位上限 | 允许类型 | 允许级别 |
|---|---|---|---|---|---|
| 三线 | 1 | 0 | 7 | circuit, shoot | normal |
| 二线 | 2 | 0 | 10 | circuit, shoot, business | normal, large |
| 一线 | 4 | 0 | 15 | circuit, shoot, business, comic | normal, large, festival, graduate, debut |
| 超一线 | 4 | 1~2 | 不限 | 全部 | 全部 |

**关键改动**：三线看到的是「同一份演出池里，≤7 顺位、且只属于普通级别的那几场」，不是「另配一套三线专属演出」。三线永远刷不出商务、漫展、OM、中外拼盘——它们是类型/级别/顺位三重过滤掉的结果，不是被城市标签写死的。

`cities.json` 另有 `weeklyCost`，本轮恒 0（城市作为成本选择这件事等 P2 的月费一起做）。

### 5.2 每周场次与刷新

每周刷新，`seed + 周序号` 派生（D-010，重算一致）。场次数量、周中随机区间全部从 `cities` 读。

- 节日周：`festival` 级别的演出进入候选池参与抽取（**不是"额外加一场"**）。非节日周它们根本不出现。
- 节日标签：`spring` 春节周、`summer` 夏日祭、`anniv` 出道周年、`newyear` 跨年。

### 5.3 抽取：按级别加权（用户要的「普通占 80%」）

```
while 还缺场次 and 池里还有演出：
  可用级别 = 池里还剩演出的级别
  按各级别 weight 加权随机选一个级别
  在该级别的剩余演出里均匀随机选一场，移出池
```

当前权重：`normal 80 / large 6 / festival 4 / sino 3 / debut 3 / birthday 2 / graduate 2`（和 = 100）。

实测分布（60 周，seed=probe-seed）：

| 城市 | 场次/周 | 级别分布 |
|---|---|---|
| 三线 | 1.00 | normal 100% |
| 二线 | 2.00 | normal 91% / large 9% |
| 一线 | 4.00 | normal 84% / large 11% / graduate 3% / debut 2% |
| 超一线 | 5.52 | normal 85% / sino 3% / large 5% / debut 3% / graduate 2% / birthday 2% |

**这是「普通 80%」的直接后果**：一周 4 场里大约 3 场普通、1 场别的。想让大场更常见，把 `normal` 的「刷新权重」调低（`shows` sheet，同级别全部改），不用动代码。

### 5.4 演出池分层（实际生效版本）

| 层 | 类型 | 出现条件 | 备注 |
|---|---|---|---|
| 普通拼盘 | circuit / normal | 三线起 | 3~10 顺位，主玩法 |
| 大型拼盘 | circuit / large | 二线起，但 ≤10 顺位才有实际命中 | |
| 中外拼盘 | circuit / sino | 仅超一线 | 12~18 顺位 |

### 5.5 阵容与 NPC 填充

**每场可报名组合数 = 该演出的顺位数**（配置决定，不再是「按城市查表」）。当前池子从 1 到 18 都有；城市靠「顺位上限」把大场挡在外面。

**NPC 填充曲线**（`d` = 距开演天数），按 `slotCount` 比例占用。
2026-11-04 改版（T-034）：**放弃 60 天线性阶梯，压力集中到报名截止前 7 天**。

| d | 填充比例 | 玩家看到 |
|---|---|---|
| d > 14 | 0 | 全部空位可报 |
| 14 | 0.05 | 全空或空 1 |
| 13 | 0.15 | 空 1～2 |
| 12 | 0.28 | 空 1～2 |
| 11 | 0.45 | 空一半左右 |
| 10 | 0.65 | 剩 1～2 |
| 9 | **1** | **已满（不可报名）** |
| 8 | **1** | **已满（不可报名）** |
| d ≤ 7 | 1 | **已宣发，不可报名** |

- 占位量：`ratio >= 1 ? N : min(N-1, round(N × ratio))`；`N-1` 这层保护保证 **d ≥ 10 时一定还有空位**。
- 填充顺序：顺位 1 → N（开场先满，压轴最后满）。压轴最贵，理应留到最后才定。
- `N = 1`（拍摄/商务/漫展）在 `d ≥ 10` 恒为空，`d = 9/8` 满 —— 单顺位通告的开窗期是 60 天里除最后 2 天的全部。
- 玩家已占的位不参与 NPC 分配。
- **「已满」与「已宣发」是两个状态**：`已满` = NPC 占满但还没到截止日（`d = 9/8`）；`已宣发` = `d ≤ 7` 截止。
  两者在列表里都沉底，但标签与底色不同（已满灰、已宣发浅橙）。
- 设计意图：平时看到的都是"能报"，只有在**截止前两天**才突然抢不到——
  让"犹豫一天"的代价体现出来，而不是让玩家在第 55 天就看到一半位置没了。

## 6. 报名状态机

```
        开演前 60 天                 开演前 7 天            开演
  [未出现] ────────▶ [可报名] ────▶ [已宣发·锁定] ────▶ [已结算] ────▶ 移入「已参与」
                        │  ▲
              报名成功  │  │ 取消（d>15 免费 / 7<d≤15 违约）
                        ▼  │
                     [已报名] ┘
```

规则：
1. **可见/可报名**：`d ≤ 60` 且 `visibleCond` 满足、城市达标。
2. **报名截止**：`d ≤ 7` 一律不可报名（含取消）。已报名者此时进入「已宣发」。
3. **同一天互斥**：同一天只能有 1 场演出的报名；再报同一天另一场 → 「这天你已经有安排了」。
4. **排程占位**：报名成功时立刻在该天写入 1 条 `fixed` 演出项（OM 占 3 槽）。占不下（当天剩余空槽不足）→ 报不了，提示「这天行程排满了」。
5. **取消**：`d > 15` 全额退；`7 < d ≤ 15` 收违约金；`d ≤ 7` 不允许。
6. **结束**：结算后从「报名演出」移入「已参与演出」，并在排程里标记 done。

## 7. 出场费与违约金

```
提成率 = clamp((玩家实际属性总和 − 该顺位要求总和) / 该顺位要求总和, 0, 0.30)
出场费 = round(baseFee × (1 + 提成率))
```
- 「实际属性」取 `effectiveStats()`（含装备加成），要求取 `reqStats` 之和（组合单则用成员合计）。
- 报名成功**立即到账**并写日志：「报名了《城东拼盘》压轴位，出场费 ¥2,340（属性超出要求 30%，已封顶）」。
- **违约金**：`7 < d ≤ 15` 取消 → 追回 `出场费 × 60%`（即玩家净得 40%），日志写明；`d ≤ 7` 不可取消。
- 违约金不扣信誉（无信誉系统，见 T-011），只记 `flags[show:x:cancelled]` 备将来用。

## 8. 组合名气度（新概念）

存 `Party.fame`（派生值，每次结算与每周刷新时重算），不手改。

```ts
fanScore  = floor((solo*3 + group*2 + dd*1 + casual*0.5) / 10)   // 忠诚四层加权
actScore  = min(1200, party.activities * 8)                       // 每参加一场演出 +1
memberScore = (party.members.length - 1) * 40                     // 团队规模（单人组合为 0）
fame = fanScore + actScore + memberScore
```

分档（用于 UI 标签与要求阶梯）：

| 档 | 名气 | 能报的层级 |
|---|---|---|
| 新人 | 0–299 | 三线开场、街演、特典 |
| 小有名气 | 300–699 | 三线全部、二线开场 |
| 有名字 | 700–1499 | 二线全部、一线开场 |
| 上升期 | 1500–3999 | 一线全部、超一线开场 |
| 顶流 | 4000+ | 超一线全部、OM |

- `party.activities` 在每场演出结算时 +1（取消不计）。
- 组合名气也决定**门票分成**的基线（§9）。

## 9. 结算五模块（item 10 的实现口径）

结算发生在演出那一条行动被 `settle` 执行时，**不走** `action_results` 表，走独立函数 `settleShow(state, booking)`。

| 模块 | 公式 | 受什么影响 |
|---|---|---|
| ① 门票分成 | `ticketBase × (0.5 + 0.5 × min(1.5, fame / 1000)) × slotMul` | 总名气 + 顺位 |
| ② 特典分成 | `goodsBase × 匹配度 × (0.6 + 0.4 × 熟练度/100)` | 曲目 + 观看粉丝构成 + 属性加成 |
| ③ 属性加成 | `statGain × (1 + min(0.10, fame / 30000))` | **只受总名气**，封顶 +10% |
| ④ 粉丝收益 | `fanGain × (0.8 + 0.4 × 匹配度)` | 粉丝构成、状态 |
| ⑤ 状态变化 | 体力 −(20 ~ 30) / 心情 +6 / 健康 −3 / 饱腹 −8 | 顺位越后消耗越大 |

- `slotMul`：开场 0.8 / 中坚 1.0 / 次压轴 1.2 / 压轴 1.4。
- `匹配度 = Σ(audience[t] × 玩家该类粉丝占比)`，取值 0–1；粉丝构成越对口，特典与粉丝收益越高。
- **曲目熟练度**：每首曲目独立 0–100，参演一次 +6（对上曲目时 +10），影响②。
- **OM / 商务 / 拍摄**不走五模块：OM 把①②③④合并成一笔「全部领取」；商务/拍摄 = 报名收益（签约时就给）+ 完成收益（结算时给），不看曲目与特典。
- 结算不触发常规事件与剧情事件（演出是独立事件），但会写一条 `kind: 'show'` 日志，含各模块明细。

## 11. 与排程的关系

- 演出**只在报名时**写排程（`fixed: true`，不可删、不可拖）。
- 玩家在安排行程弹窗里能看到它，但只能通过「演出 → 取消报名」移除。
- 演出日其余槽位仍可排普通行动（拼盘 1 槽 / OM 吃满 3 槽）。
- 当天剩余空槽不足 → 报不了。这是唯一「演出与行程打架」的入口，提前挡掉。
- `advance()` 的前置判定（T-031）对演出项生效：体力为负门槛时照样拦。

## 14. 我拿不准、先按保守写的三处

- **签了名但当天日程被别的东西占满**：只在报名时校验，报名后不再校验（玩家自己别把那天塞满）。若你希望「报名即锁定整天」，告诉我，我改成占满 3 槽。
