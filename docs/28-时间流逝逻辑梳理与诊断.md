# 时间流逝逻辑梳理与诊断

> 2026-11-03。起因：「时间流逝一直没有正常运行」。
> 本文只做两件事：把从点「开始推进」到进度落库的**每一步公式**摊开；指出**尺度在哪一层错位**。
> 结论基于云端真实存档核对，不是推测。

## 0. 结论先行

时间不是「不走」，是**慢到看不出来**。两个尺度没有对齐，缺陷叠加：

| | 实际值 | 应该是什么 | 后果 |
| --- | --- | --- | --- |
| 一条行动占多久（内容表） | **1 游戏分钟**（演出 3） | 10 游戏分钟（D-014） | 行动只占槽位的 1/10 |
| 槽位间距（排程算法） | **10 游戏分钟** | 同上 | 每条行动后面空 **9 分钟** |
| 1 真实毫秒推进多少游戏时间 | **1 毫秒**（speed=1） | 应有独立换算系数 | 9 分钟空洞 = **9 真实分钟** |

三者相乘的结果：点开始 → **干等 9 分钟** → 跑完 1 分钟的一条 → 再等 9 分钟。
一天 3 条，共 **30 真实分钟**。这正是「时间流逝没在运行」的体感来源。

### 0.1 它是怎么变成这样的（git 溯源）

```
de53aee → 65bbee6 → 8d2a42c : balance.actionMinutes = 1     ← 测试临时值
ed1c399  「内容源切到 all.xlsx」    : actionMinutes = 1 → 10   ← 只改了槽位
```

那一次只把 `balance.actionMinutes` 从 1 改成 10（D-014 落地），**但 `actions` 表的「单次分钟」没跟着从 1 改成 10**。
在 `actionMinutes=1` 时期，槽宽 1 分钟、行动 1 分钟，首尾正好相接，所以跑得动；
改成 10 之后，槽宽 10 分钟、行动仍 1 分钟，于是每条后面多出 9 分钟。

云端那 58 条排程里，前 29 个间隔是 0（旧档、`actionMinutes=1` 时期排的），
后 10 个间隔是 9 分钟（T-027 槽位制之后排的）——**这两段数据的差异就是这次改动的化石**。
所以不是「从来没对过」，而是**从 `ed1c399` 起就再没对过**。

## 1. 三个时间量，别混

| 名称 | 载体 | 单位 | 说明 |
| --- | --- | --- | --- |
| 游戏时间 | `RunState.at` = `ClockState.gameAt` | 毫秒，绝对刻度 | 从 `START_AT` 起算；**日历按行动走，一天 = 30 游戏分钟**，不是 24 小时 |
| 真实时间 | `Date.now()` / `performance.now()` | 毫秒 | 客户端与服务端各自取，服务端那份才算数 |
| 倍速 | `ClockState.speed` | 无量纲 | **真实 1 毫秒 → 游戏 `speed` 毫秒**。⚠️ 当前没有独立换算系数，speed=1 就是 1:1 |

关键公式（客户端与服务端**必须完全一致**，现在是一致的）：

```
目标游戏时间 = 水位线 gameAt + (现在真实时间 - 锚点 wallAnchor) × speed
```

## 2. 常量表（当前实际生效值）

| 常量 | 值 | 来源 | 用途 |
| --- | --- | --- | --- |
| `actionMinutes` | **10** | `balance.json` | D-014 的尺度基准 |
| `ACTION_MS` | 600 000 游戏毫秒（10 游戏分钟） | 派生 | **槽位宽度**、行动时长缺省值 |
| `dailySlots` | 3 | `balance.json` | 每天行动位 |
| `DAY_MS` | 1 800 000（30 游戏分钟） | 派生 | 日历一天 |
| 行动 `durationMinutes` | **1**（30 条）/ **3**（5 条演出） | `actions` 表 | **行动真实占用** ← 与 `ACTION_MS` 不一致 |
| `SHOW_DURATION_MS` | 1 800 000（30 游戏分钟） | 派生 | 演出占满整天 |
| `START_AT` | 2026-01-01 09:00 UTC | `content.ts` | 周目起点，客户端 `T0` 同源 |
| `runDays` | 730 | `balance.json` | 两年 |

## 3. 完整链路

### 3.1 排程怎么落位（`core/src/plan.ts` `placeAction`）

```
span = ceil(行动时长 / ACTION_MS)     // 1 分钟行动 → 1 槽；30 分钟演出 → 3 槽
候选起点 = 当天起点 + 槽号 × ACTION_MS
```

一天 3 槽，槽宽 10 分钟 → 三个合法起点是 `第0/10/20 分钟`。
行动只占 1 分钟 → `09:00–09:01`、`09:10–09:11`、`09:20–09:21`，**每条后面空 9 分钟**。

### 3.2 在线推进（`App.tsx` tick，~100ms 一次）

```
anchorGame = max(run.at, 已显示的游戏时间)
target     = max(run.at, anchorGame + (nowPerf - anchorPerf) × speed)
settle(run, schedule, run.at, target, seed, { endAt: RUN_END_AT })
```

`settle` 只结算**整条**行动：`if (item.endAt > to) { stoppedReason = 'time'; break; }`。
所以 target 必须**真的一步步走到 `endAt`** 才会执行，中间的空档不会被跳过（空档返回 `time`，不会触发 heal）。

结论：一条 1 分钟行动后接 9 分钟空档，在 speed=1 下就是 **540 真实秒的等待**。

### 3.3 结算（`core/src/settle.ts`）

- 只跑完整行动；随机数按 `seed:action:行动id` 派生（D-010），可被服务端逐字重放。
- 每条之后 `autoAcceptTasks`、常规事件、剧情事件（major 事件中断时间）。
- `stoppedReason` 取值：`time`（时间不够跑下一条）/ `exhausted`（没有可跑的）/ `event` / `stamina` / `money` / `stopped` / `ending`。
- 只有 `time` 与 `exhausted`（且排程还有未完成项）不停止；其余都会让客户端 `setRunning(false)`。

### 3.4 上报与校验（`/v1/sync`）

客户端每完成一条行动上报一次（`to = run.at`），服务端：

```
allowed = clock.gameAt + (now - wallAnchor) × speed + 1000   // 1 游戏秒容差
to > allowed              → 409 too_fast（判为改档）
to < clock.gameAt         → 409 stale
replay ≠ 客户端 run       → 409 mismatch（以服务端重放为准）
```

### 3.5 离线补算（`server/src/clock-service.ts` `loadAndCatchUp`）

所有读路径（开屏 / start / pause / 上报 / 抉择）都会先补算到「现在」。公式与 §3.2 相同，
所以**离线也按同一节奏**：离开 10 分钟 = 推进 10 游戏分钟 = 跑掉 1 条行动 + 走完 1 段空档。

### 3.6 暂停 / 继续 / 改倍速

| 操作 | 服务端动作 |
| --- | --- |
| 开始 | `status=running`，`wallAnchor=now`，`gameAt=run.at` |
| 暂停 | 先补算，再 `status=paused`，`wallAnchor=0`（时间冻结） |
| 继续 | 同「开始」，重新锚定；未完成的那条**重新跑**，不作废 |
| 改倍速 | 先 pause 再 start(speed)；白名单 `[1,2,4,8]` |

### 3.7 刷新恢复

1. 拉云端最新档（`revision` 大则覆盖本地）
2. `GET /v1/clock/session` 取权威时钟（失败重试 1 次，仍失败给手动重试入口）
3. `status=running` → 本地接着播放；`paused`/`idle` → 停在原地提示「点继续」

## 4. 实测证据（2026-11-03 21:30，你正在玩的那一局）

```
run.at = gameAt = 1767285120000   status = running   speed = 1
58 条排程：行动占用全部 1 分钟（{1: 58}）
空档分布： 9 分钟 ×10   27 分钟 ×13   0 分钟 ×29（旧档）
样例：09:00–09:01 / 09:10–09:11 / 09:20–09:21   跨天 18:00–18:01 → 次日 09:00
```

- 行动一条都没跑完，是因为 `run.at` 停在 16:32，下一条 `startAt=16:40` → 需先走 **480 游戏秒**（下一条开始），再加 60 秒，共 540 秒。
- speed=1 → **540 真实秒**。所以你会看到倒计时从「还剩 540 秒」开始，每秒只掉 1 秒。
- 旧档那些 `0 分钟空档`（首 29 条）是 T-027 之前排的，首尾相接，所以**那时跑得动**；改成槽位制后才出现 9 分钟洞。

## 5. 五个问题（按严重度）

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| P0-1 | 行动时长（1 分钟）≠ 槽位宽（10 分钟） | 58/58 条都是 1 分钟，空档 9 分钟 | 每条行动后空转 9 分钟 |
| P0-2 | 缺「真实 ↔ 游戏」换算系数，`speed` 直接当毫秒倍率 | tick 与服务端公式都是 `× speed`，无 TIME_SCALE | 1 游戏分钟 = 1 真实分钟，整体慢 60 倍量级 |
| P1-1 | `speed` 只写不读 localStorage | `App.tsx:275` `useState(1)`，1212 行只 setItem | 刷新回到 1×，玩家以为改倍速没用 |
| P1-2 | 上报容差 1 秒 < 起播延迟 | 起播请求往返 1.2 s，客户端已推进 1.2 s | 高倍速（8×）下首次上报必 `too_fast` → 被拽回 |
| P2-1 | 文档从未定义「1 行动 = 多少真实秒」 | `docs/12 §3` 只写「由行动耗时决定」，是同义反复 | 无法验收，每次改数值都靠感觉 |

## 6. 修法（需要拍板）

### 方案 A：把行动时长填满槽位（改内容表）

`actions.durationMinutes`：普通行动 `1 → 10`，演出 `3 → 30`（或让 `SHOW_DURATION_MS` 直接取 `durationMinutes`）。
- 优点：符合 D-014；槽位不再有洞；时间轴、日历、任务时限全部自洽。
- 代价：改 `content/all.xlsx` 的 `actions` 表（策划独占）；`action_results` 不受影响。

### 方案 B：槽位宽改用行动时长（改算法）

`placeAction` 的槽宽由 `ACTION_MS` 改为 `durationMs`，同时 `DAY_MS` 跟着变。
- 优点：不动内容表。
- 代价：一天变成 3 游戏分钟，与 D-014 冲突；任务时限、房租周期、周目长度全部要重排。**不建议**。

### 方案 C：引入独立换算系数 `TIME_SCALE`（改代码，必做）

```
真实 1 秒 → TIME_SCALE 游戏秒
目标游戏时间 = gameAt + (now - wallAnchor) × speed × TIME_SCALE
```
倍速 `1/2/4/8` 乘在 `TIME_SCALE` 之上，语义变成「再快 2/4/8 倍」，符合玩家直觉。

推荐 **A + C**。取 `TIME_SCALE = 20`（1 真实秒 = 20 游戏秒）时的体感：

| | 现在（1:1，无 TIME_SCALE） | A+C，TIME_SCALE=20 |
| --- | --- | --- |
| 一条行动 | 60 s | **30 s** |
| 行动后空档 | 540 s | **0**（A 消除） |
| 游戏内一天（3 行动） | 1 800 s（30 min） | **90 s** |
| 游戏内一周 | 3.5 h | **10.5 min** |
| 两年周目 | 365 h | **18.3 h** |
| 8× 时一条行动 | 7.5 s | **3.75 s** |

参数由 `TIME_SCALE` 一个数控制，想更慢调小、想更快调大，不必再动 `actionMinutes`。
