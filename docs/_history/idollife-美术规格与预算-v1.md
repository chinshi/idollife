# 《idollife》美术规格与预算 — 主角 Live2D

> 版本 v1 ｜ 2026-11-02 ｜ 资产代号 `idol_hero_01` ｜ 目标引擎：Live2D Cubism 5（导出 Cubism 4 runtime）
> 显示尺寸：窗口内 260×360，人物页 480×720 ｜ 机型档位：办公机集显 / WebGL1 保底
> 关联：[美术风格提案](idollife-美术风格提案.md)（造型、色彩、禁忌以提案为准，本文只管"怎么落地"）

## 0. 结论先行

1. **组合数是免费的，部件数是贵的**。2 发型 × 4 发色 × 3 上衣 × 3 裤袜 × 5 饰品 = **1,728 种外观，只需要 20 组素材**。前提是所有部件共用同一画布、同一锚点、同一参数表——这三件事画之前必须定，定了之后再改等于重做。
2. **换装走程序侧 part opacity，不建模型参数**。理由见 §2.3。
3. **发色用"每色一组完整上色"，不用灰度 × 正片叠底**。多画 6 组、每组 1 小时，换来零 runtime 风险。
4. **纹理预算 20MB（P0）/ 32MB（含全身）**——Web 端不能压纹理，这是这套方案最贵的一笔。
5. 总工作量 **41 人日**（熟手单人 5–7 周，含返工 8–10 周）。

### 1.3 发色实现：两方案，选 B

| 方案 | 做法 | 素材量 | 风险 |
|---|---|---|---|
| A 灰度 + 正片叠底 | 每发型 1 张灰度明暗图 + 1 个可换纯色 multiply 层 | 2 + 4 | Web runtime 的 multiply 混合与 PNG 量化叠加后易出色阶断层，**需实测** |
| **B 每色一组完整上色（推荐）** | 2 发型 × 4 发色 = 8 组完整上色 drawable，共用同一网格与线稿 | 8 | 零 runtime 风险，只多 6 组填色（≈6 小时） |

**选 B。** 只有当发色要扩到 10 色以上（素材量线性爆炸）时，才值得回头做方案 A。

**发色硬约束**：所有发色必须落在 **L 10–45** 区间。超出会破坏"深色人形"的缩略图轮廓（见提案 §2 硬规则 3）。

### 1.4 命名规范

```
{组}_{款式}_{序号}          hair_A_front_01
                            top_rehearsal_body
                            leg_kneehigh_01
                            acc_head_clip_01
                            exp_tired
```

- 组名固定 12 个：`body / face / hair_A / hair_B / hair_C / top / leg / acc_head / acc_neck / acc_ear / acc_wrist / exp`
- 序号从 `01` 起，两位；不出现中文、空格、大写
- Part ID 用同名前缀：`Part_hair_A`、`Part_top_02`（程序侧按 Part ID 切换，见 §2.3）

### 2.3 换装怎么实现：走程序侧

| 做法 | 代价 | 结论 |
|---|---|---|
| 模型内参数驱动（`ParamSwitchHair` 0..4 + 每组 opacity 阶梯） | 参数爆炸（5 槽 = +5 参数 × 每部件 3 段关键帧），Cubism 里极易做错，且导出 runtime 后调试困难 | ❌ |
| **程序侧 part opacity（推荐）** | 前端一行：`coreModel.setPartOpacityById('Part_hair_A', 0/1)` | ✅ |

- 每个可选部件是一个独立 Part，互斥组内同一时刻只有 1 个 opacity = 1，其余 = 0。
- 切换时**必须补一个 0.12s 的遮罩**（换装动作 `switch_pose`），否则玩家会看到 1 帧"两个发型叠在一起"。这是最容易被忽略的观感 bug。
- 保底：若实测发现 opacity 切换有闪烁，退化为"两套完整模型切换 + 交叉淡入"，代价是显存翻倍（需重新评估 §3）。

| 侧发 | ±4° | 0.15 | 0.60 | |

### 2.5 动作清单（无交互，全靠这几组撑"活着"）

| 动作 | 时长 | 循环 | 内容 | 随机化 | 触发 |
|---|---|---|---|---|---|
| `idle_normal` | 8.0s | 是 | 呼吸 ×2、眨眼 ×2–3、视线游移 ×1、重心微移 ×1 | 眨眼间隔 2.8–5.4s / 视线 6–14s / 重心 18–26s | 常驻 |
| `idle_tired` | 10.0s | 是 | 头低 4°、闭眼 0.45s（正常 0.12s）、呼吸振幅 ×0.7 | 同上，区间拉长 1.5 倍 | 体力 < 30% |
| `idle_stage` | 6.0s | 是 | 头抬 3°、发梢振幅 ×1.6、嘴微张 | — | 演出事件 |
| `switch_pose` | 0.25s | 否 | 遮罩淡入 0.12s → 部件切换 → 头发惯性回弹 | — | 换装 |
| `exp_01..06` | 0.15s | — | 表情混合（Expression，不占动作槽） | — | 事件 |

**为什么必须随机化**：固定 8 秒循环，玩家 30 秒内就会识破"这是个 GIF"。眨眼间隔、视线、重心三个变量各自独立随机，是"活的"和"循环的"之间唯一的差别。这一条不实现，前面所有美术投入都白费。

## 3. 纹理与显存预算

### 3.1 计算口径

Web 端**不能压纹理**（浏览器不支持 ASTC/ETC2，解码后就是 RGBA32）。所以显存 = 宽 × 高 × 4 字节，没有折扣。用 `asset_budget.py` 实测：

| 方案 | 纹理 | 显存 | 适用 |
|---|---|---|---|
| **P0（推荐）** | 1×2048² + 1×1024² | **20.00 MB** | 半身 + 3 上衣 + 2 发型 + 4 发色 |
| 进阶 | 2×2048² | **32.00 MB** | 加舞台服 + 全身 + 季节限定 |

脚本输出（进阶方案）：`live2d_atlas_01_2048 16.00MB 50% / live2d_atlas_02_2048 16.00 MB 50% / 合计 32.00 MB / 预算 96 MB → 在预算内`。

### 3.2 图集策略

- 换装部件**全部常驻图集**（不做运行时换贴图）——所以"部件总数"会推高图集，"组合数"不会。这是 §0 结论 1 的另一面。
- 分页原则：第 1 页放"永远在场"的东西（脸、身体、默认发/衣），第 2 页放可选件。这样 P0 只用 1 页 2048 就能跑，P1 加第 2 页。
- 禁止 4096² 单页：集显与移动端 Safari 都可能直接失败。

### 3.3 包体

| 项 | 估算 | 备注 |
|---|---|---|
| `live2dcubismcore.min.js` | ≈ 190 KB | 待实测 |
| `pixi-live2d-display` + pixi | ≈ 130 KB（gzip） | 当前项目无 WebGL 层，这是净新增 |
| 纹理 PNG（pngquant 量化后） | 1.5–2.5 MB | 20MB 显存对应这个量级 |
| `moc3` | 0.3–0.6 MB | |
| **首包净增** | **≈ 3–4 MB** | |

> 一个文字游戏的包体只有几百 KB，+3–4MB 是显著变化。**必须懒加载**：进人物页才拉模型，先用 L0 静态图占位。

## 7. 假设与待确认

**假设（待确认）**
1. 假设：半身到大腿中段，不做全身——若要做全身，纹理必升到 2×2048（32MB），人日 +18。
2. 假设：换装切换由前端调用 part opacity，不在模型内做参数——需前端确认可改 `coreModel`。
3. 假设：单角色，不做 NPC 同款模型（NPC 用 L0 静态图）。
4. 假设：先按 P0 的 20 组素材排期，P1 看数据再加。

**待确认决策**
- D1 组合合法性白名单是否由内容表（`content/all.xlsx`）配置——涉及是否需要给配置表加一列。
- D2 表情数量：P0 是 6 个够不够（够则省 2 人日）。
- D3 是否接受首包 +3–4MB（决定要不要走 L1）。
