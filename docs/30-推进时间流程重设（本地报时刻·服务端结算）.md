# 30 · 推进时间流程重设（本地报时刻 · 服务端校验结算）

> 状态：设计定稿 v4，待实施（T-039）
> 决策日期：2026-11-04
> 前提：**离线挂机是核心玩法**（关掉页面时间照走，回来一次补齐）
> 修订链：v1「步进结算、无时钟」作废 → v2「服务端自取 now 推进」→ v3「客户端报 targetAt，服务端校验上界后结算」→ **v4「去掉倍速，恒 1×」**
> 取代：docs/28 的双引擎结论；T-029「客户端写结算结果」；T-036 的接管/只读体系
> v4 变更：产品所有者 2026-11-04 拍板**取消倍速**，时钟不再有 `speed`，全部按 1× 推进。

## 1. 一句话

**客户端只回答「现在该推进到哪个游戏时刻」，服务端只回答「这能不能发生」和「这段时间的收益」。**

| 谁 | 负责 | 不负责 |
|---|---|---|
| 客户端 | 按 `wallAnchor` 画进度条 / 倒计时（纯算式）<br>算下一条行动的 `endAt`，作为 `targetAt` 上报<br>把服务端返回的 `executed` 播出来 | **不算收益**、**不写时间**、**不落任何权威状态** |
| 服务端 | 校验 `targetAt` 是否在上界内（核时间）<br>`settle` 出这段时间的全部结果（算收益）<br>落库并下发权威 `run` / `schedule` | **不主动推进**（没人报就不算）<br>**不在读路径算**（`GET` 只读） |

一句话验收：**客户端说「我要到 T」，服务端说「你最多只能到 M，而且到 M 的结果是这个」，客户端整份接受。**

## 1.5 时间尺度：只有一个变量 `timeScale`

**倍速已取消**（v4）。时钟恒以 1× 推进，唯一能改节奏的是配置表的 `timeScale`（开发期测试加速开关）。

| | 测试态（当前 `balance.timeScale=20`） | 生产态（上线 `timeScale=1`） |
|---|---|---|
| 一条行动（10 游戏分钟） | **30 秒** | **10 分钟** |
| 一天（3 条） | 90 秒 | 30 分钟 |
| 排 7 天（21 条）耗尽 | 10.5 分钟 | **3.5 小时**（= 210 分钟，产品所有者核算确认） |
| 离线 8 小时可推进 | 960 条（320 天行程） | **48 条（16 天行程）** |

- `TIME_SCALE` 已从 `BALANCE.timeScale` 读取（`content.ts:17`）。**任何新代码不得写死 20**，客户端也不得另算一套系数。
- 上界 / 锚点公式本身带 `timeScale` 因子，切生产口径**不需要改代码**，只改配置表。
- 本文与派单卡里的秒数，未标注「生产」的一律指**测试态**。
- 手工验收只能用测试态跑——生产态下行动 10 分钟一条，等不到结算。

> **`gameAdvance(elapsed, speed, timeScale)` 的 `speed` 参数保留**（core 的 D-017 唯一换算公式，测试也在用），但**时钟层固定传 1**，`ClockState` 里不再有 `speed` 字段。这不是留后门，是让换算公式与产品开关解耦。

## 2. 安全边界：上界校验（唯一防线）

时间在本地算，所以「到哪一刻」由客户端提。唯一防住伪造的就是这条公式：

```
maxTargetAt = clock.status === 'running'
              ? clock.gameAt + gameAdvance(serverNow − clock.wallAnchor, 1) + 500
              : clock.gameAt
```

- `clock.wallAnchor` 的语义：**`clock.gameAt` 这个游戏时刻，对应的服务端墙钟时刻**。
- `serverNow` 是服务端自己的墙钟，客户端碰不到 → 上界无法伪造。
- `+500` 是游戏毫秒容差（对 10 分钟的行动是 0.08%）。
- `paused` 时上界 = `gameAt`，客户端不可能凭空推进。

**推进后 wallAnchor 只前移、不重置**：

```
newWallAnchor = oldWallAnchor + (newGameAt − oldGameAt) / max(1, timeScale)
```

这样网络延迟造成的时间余量不会被吞掉。例：一条行动 10 分钟，网络慢 0.5 秒，服务端在 600.5 秒时收到 → 上界是 600.5 秒的量，实际消费 600 秒的量，剩 0.5 秒额度留到下次。

三种判定结果：

| 情况 | 服务端 | 返回 |
|---|---|---|
| `targetAt ≤ maxTargetAt` | 按 `targetAt` 结算 | `clamped: false` |
| `targetAt > maxTargetAt` | 裁到 `maxTargetAt` 结算 | `clamped: true` + `clampedTo`，客户端整份覆盖并出提示「时间校准：已回退到服务器时间」 |
| `targetAt ≤ clock.gameAt` | 视为已推进过 | `executed: []`，幂等返回 |

> **「时间对不上就改客户端」的正确含义**：不是差分修补某个字段，而是返回服务端权威的 `run` / `schedule` / `clock`，客户端**整份覆盖**。差分修补需要两套判断规则，那正是现在这堆 bug 的来源。

## 3. 数据

```
RunRecord = { userId, runId, revision, seed, run, schedule, clock, updatedAt }

clock = {
  status: 'running' | 'paused',
  gameAt: number,      // 已结算到的游戏时间（不变量 === run.at）
  wallAnchor: number   // gameAt 对应的服务端墙钟；paused 时保留但不参与计算
}
```

- **删除 `speed`**（v4 取消倍速）：时钟恒 1×，节奏只由 `timeScale` 决定。
- **删除 `sessionId`**：客户端不写时间，没有可抢占的东西。
- **删除 `idle` 状态**：只剩 running / paused 两态。
- `ownerId` 账号隔离保留（T-036 那部分仍有效）。
- 旧档的 `sessionId` / `localClock` / `speed` 读时忽略，不迁移。

### 3.1 权威归属（防止误读「只校验上界」）

**「只校验上界」说的是一个请求参数，不是服务端不存时间。** 服务端是唯一的存档方与唯一的时间来源：

| 事实 | 存在哪 | 客户端有没有副本 |
|---|---|---|
| 行程（每条行动 / `startAt` / `endAt` / `done`） | 服务端 `RunRecord.schedule` | 有内存副本 + localStorage 只读缓存，**写入必须经 `PUT /v1/state` 回包确认** |
| 全部游戏状态（钱 / 体力 / 粉丝 / 属性 / flags / log） | 服务端 `RunRecord.run` | 同上，只读缓存 |
| 挂机起点（wallAnchor）与已结算到的游戏时刻（gameAt） | 服务端 `RunRecord.clock` | **不存**，每次 `GET` 取回 |
| 当前时间 | 服务端的墙钟 | 客户端只用 `serverTime − Date.now()` 求偏移，**永不自行推进** |

三个场景的时间都从服务端来，不依赖任何一台设备的本地状态：

| 场景 | 流程 |
|---|---|
| **换设备 / 新浏览器** | `GET /v1/state` → 拿到 `clock{gameAt, wallAnchor}` → 按 `gameAt + (serverNow − wallAnchor) × timeScale` 算出 `gameNow` 画进度条 → `advance { targetAt: null }` 补齐到上界。旧设备不需要在场，也不需要交接。 |
| **刷新 / 重开页面** | 同上。`GET` 纯读，不改任何字段。 |
| **断网回来** | 断网期间界面按最后一次拿到的 `wallAnchor` 继续画（只是视觉），不产生任何结果；恢复后一次 `advance { targetAt: null }` 由服务端补齐并回放。 |
| **两台设备同时在线** | 各自按同一份 `clock` 画，`advance` 由 `expectedRevision` CAS 裁决，输的一方 409 → 重新 `GET` 后再报一次（幂等，不会多算）。 |

**因此 `targetAt` 的定位要写清**：服务端本来就算得出 `maxTargetAt`（=「现在应该到哪」）。客户端报 `targetAt` 只有一个用途——**声明「我在这个停点想要结果」**（通常是下一条行动的 `endAt`，好让每条结果单独回放）。它不能改变服务端认为的当前时间，也不能让服务端多算或少算：

- 报 `null` → 服务端一路补到上界（离线补齐、断网回来、贪快进都走这条）
- 报 `nextStopAt ≤ 上界` → 结算到这个停点，逐条出结果
- 报 `> 上界` → 裁到上界（`clamped: true`，客户端整份覆盖）

**两层安全各自管一件事，不要混**：

| 层 | 防什么 | 靠什么 |
|---|---|---|
| 内容层 | 玩家改钱 / 改粉丝 / 改体力 | 客户端**根本不上报 state**，服务端从 `baseRevision` 那份存档**重放**出结果 |
| 时长层 | 玩家改系统时钟多要时间 | 上界用 `serverNow` 与 `wallAnchor` 算，客户端碰不到 |

上界只防「时长伪造」，不承担内容正确性——内容正确性由「服务端算、客户端只接收」保证。

## 4. 端点

### 4.1 `POST /v1/advance` —— 唯一推进入口

body：`{ expectedRevision, targetAt? }`

1. auth 失败 → 401；`runId` 缺失 → 400
2. 记录不存在 → 404（新档必须先 `PUT /v1/state`）
3. `rec.userId !== user.id` → 403
4. `expectedRevision !== rec.revision` → 409 `conflict`（回包带当前存档）
5. `targetAt` 缺省 → `targetAt = maxTargetAt`（**启动、刷新、离线回来**都走这条，一次补齐）
6. `clampedTarget = min(targetAt, maxTargetAt)`，`clamped = targetAt > maxTargetAt`
7. `settle(run, schedule, clock.gameAt, clampedTarget, seed, { endAt: RUN_END_AT, maxSteps: 2000 })`
8. 推导新 `status` / `wallAnchor`（见 §6）
9. 有推进或状态变化才落库（`revision + 1`）
10. 返回：

```
{
  run, schedule, revision, seed,
  clock: { status, gameAt, wallAnchor },
  executed: string[],        // 本次结算的行动 id，最近 60 条以内
  stepped: number,           // 本次结算条数（可能 > executed.length）
  stoppedReason: StopReason,
  nextStopAt: number | null,
  clamped, clampedTo,
  serverTime
}
```

> `stepped` 超过 60 时，`executed` 只给最近 60 条，客户端提示「行程走了 N 条」用 `stepped`。避免离线一次返回上千个 id。

### 4.2 `GET /v1/state` —— 纯读，绝不结算

返回 `{ run, schedule, revision, seed, clock, nextStopAt, serverTime }`。

**读路径不推进**，这是 T-039 相对 T-029 的硬性翻转：刷新页面不再产生任何副作用，也不再抢主。客户端要推进就显式发 `advance`。

### 4.3 `PUT /v1/state` —— 状态变更（行程 / 组合 / 送礼 / 抉择 / 起名）

body：`{ expectedRevision, run?, schedule? }`

1~4 同上
5. **`run.at !== rec.run.at` → 409 `stale_clock`**（客户端必须先 `advance` 到最新再来改）
6. 记录不存在 → 创建（`revision: 0` → 落 1，`clock: { status:'paused', gameAt: run.at, wallAnchor: 0 }`）
7. schema 校验（`run.at` / `run.stamina` / `run.stats.vocal` 是 number，`run.log`、`schedule` 是数组）→ 失败 400
8. 落库 `revision + 1`，返回完整状态

**不做任何结算。**

### 4.4 `POST /v1/start` —— 开始挂机

body：`{}`（v4 起无参数，不再接受 `speed`）

1. auth / 归属
2. 无未完成排程 → 409 `no_schedule`；`run.pendingEvent` 非空 → 409 `pending_event`
3. **已 running → 幂等返回**（v4 起没有「改速」这个动作）
4. paused → 落 `{ status:'running', gameAt: run.at, wallAnchor: serverNow }`，`revision + 1`
5. 返回状态

### 4.5 `POST /v1/pause` —— 停止

body：`{ targetAt? }`

1. auth / 归属
2. running → 按 §4.1 第 5~8 步补算到 `min(targetAt ?? maxTargetAt, maxTargetAt)`，再置 `status='paused'`
3. paused → 幂等返回
4. 返回状态（同 `GET`）

### 4.6 删除

`/v1/sync`、`/v1/clock/start`、`/v1/clock/pause`、`/v1/clock/session`、`/v1/clock/event`、`/v1/clock/takeover`、`sameSnapshot`、`allowedGameAt`、`gapHeal`、`lost_pause`、`loadAndCatchUp`、`saveClock`、`clockTarget` 的服务端调用点、`sessionNotOwner` 全部分支，以及 **`ALLOWED_SPEEDS` / `bad_speed`**。

## 5. 客户端流程

### 5.1 渲染（不结算）

```
serverNow = Date.now() + offset            // offset 每次回包用 serverTime − Date.now() 校准
gameNow   = clock.status === 'running'
          ? clock.gameAt + (serverNow − clock.wallAnchor) × TIME_SCALE
          : clock.gameAt
```

100ms timer 只做两件事：更新进度条 / 倒计时，判断是否到了 `nextStopAt`。
**删除**：tick 里的 `settle`、`markExecuted`、`repairChain`、过期清理、3 帧丢弃、`batchRef` / `endBatch` / `snapshot`。
**删除**：`speed` state、`setSpeed`、`localStorage['idollife:speed']`、`TimeAxis` 的 1×/2×/4×/8× 按钮。

### 5.2 启动（含离线补算）

```
GET /v1/state            // 拿 run / schedule / clock，不结算
  └─ clock.status === 'running'
       → POST /v1/advance { targetAt: null }        // 服务端补算到上界
       → stepped > 0 → 顶部「你不在的这段时间，行程走了 N 条」+ 回放最近若干条
```

### 5.3 在线推进

```
算 nextStopAt（下一条未完成项的 endAt）
wait = clamp((nextStopAt − gameNow) / TIME_SCALE, 200, 15000)
到点 → POST /v1/advance { targetAt: nextStopAt }
     ├─ executed 非空 → 回放（逐条 280ms，>8 条折叠「…另外 N 条」）
     ├─ clock.status 变 paused → 停止唤醒，出停点原因（复用 STOP_TEXT / advanceBlockText）
     └─ 否则 → 用返回的 nextStopAt 排下一次
```

15 秒是心跳兜底：即使 `nextStopAt` 算错，最多 15 秒对齐一次。

### 5.4 断网

- 进度条按 `wallAnchor` 继续走（视觉时间不断，符合挂机直觉）
- 顶部标「未连接云端」，**不预测任何结果**
- 恢复后发一次 `advance { targetAt: null }` 补齐并回放

> 不做本地预演：行动粒度 10 分钟（测试态 30 秒），等一次往返无感；预演一旦偏差就会「倒退」，比等更难接受。

### 5.5 运行中改状态（行程 / 送礼 / 组合 / 抉择）

```
POST /v1/advance { targetAt: null }   // 静默对齐到最新，不打断玩家
  → 拿到权威 run（run.at 已是最新）
  → 本地应用变更
  → PUT /v1/state { expectedRevision, run?, schedule? }
```

**不暂停**、不弹「已暂停，继续请点开始推进」。玩家改完行程，时间继续走。

### 5.6 停止

`POST /v1/pause`（服务端补算到上界，玩家看到的就是停在此刻的结果）。

**v4 起没有倍速**：`TimeAxis` 上那一排 1×/2×/4×/8× 按钮整块删除，「开始推进 / 停止」两个按钮足够。

### 5.7 多设备

客户端不写时间 → 两台只会显示各自的 `gameNow`，都受同一上界约束。
并发 `advance` 由 `expectedRevision` CAS 裁决，输的一方 409 → 重试一次即可（重试会拿到对方已推进的结果，幂等无副作用）。
**删除 T-036 的接管按钮、只读横幅、`taken_over` 拦截**；`ownerId` 账号隔离保留。

## 6. 推进后的状态推导

| `settle` 结果 | 新 status | 新 wallAnchor |
|---|---|---|
| `'time'`（时间用完但排程还有） | running | `旧锚 + 已推进量 / timeScale` |
| `stepped >= maxSteps`（没算完） | running | 同上 |
| `'exhausted'` 但排程仍有未完成项 | running | 同上 |
| `'event'` / `'stamina'` / `'money'` / `'stopped'` / `'ending'` | paused | 保留原值（不参与计算） |
| `'exhausted'` 且全部 `done` | paused | 同上 |

`nextStopAt`：
- `status !== 'running'` → `null`
- 无未完成项 → `null`
- 否则 → 下一条未完成项的 `endAt`（`endAt` 缺失则 `startAt + ACTION_MS`）

## 7. 停点判定表（验收逐条对）

| 场景 | 期望 |
|---|---|
| 排程 3 条、资源足、无事件 | 全部走完，`stoppedReason='exhausted'`，`status='paused'` |
| 第 2 条带 `stopAfter` | 停在它结束，`'stopped'` |
| 下一条体力不足 | `gameAt` 停在**上一条结束**处（不前进到它开始），`'stamina'` |
| 触发重点事件 | 停在事件处，`'event'`，`pendingEvent` 非空，`paused` |
| 中间空档（某天只排 1 条） | 空档被跨过，`gameAt` 落到下一条结束，无「对齐」副作用 |
| 离线 8 小时 | `advance { targetAt: null }` 补算完成，`gameAt` 前进量 ≈ 墙钟 × `timeScale`；排程走完即停（生产态排 7 天约 3.5 小时走完，见 §9.1） |
| 上报 `targetAt` 超上界 | 裁剪结算，`clamped: true`，客户端整份覆盖 + 提示 |
| 上报 `targetAt ≤ gameAt` | `executed: []`，幂等 |
| 排程走完再 `start` | 409 `no_schedule` |

### 8.3 手工（真实服务端 + 真实组件，不许手写假数据）

1. 排 3 条 → 开始推进 → 每条到点自动结算，进度条连续无跳变
2. 开始推进 → **关页面 5 分钟** → 打开 → 出战报。测试态应结算 **10 条**（300 秒 ÷ 30 秒）。校验 `gameAt` 前进量 ≈ 真实秒数 × `TIME_SCALE`（**先 `console` 打印实际读取到的 `TIME_SCALE`，确认是 20 而不是写死值**）
3. 清空 → 只排爆睡 → 体力 0 → 推进 → 体力 40
4. 推进中改行程 → 不暂停、时间继续走 → 下一次 `advance` 用新排程
5. 断网 → 进度条继续 → 恢复 → 一次补齐，无倒退
6. 两个窗口同账号 → 都显示同一时刻，不互抢，最高频只有一次 409 重试
7. 把本机系统时间调快 2 小时 → 推进 → **不额外获得进度**（`clamped: true`）
8. **界面上不存在任何倍速按钮**（1×/2×/4×/8× 已删除）

### 8.4 回归底线

`advance` 是纯增量，**必须不破坏**：`preflight`（T-031）、`advanceBlockText` 横幅（T-035）、`nextPendingItem` 排序（T-038）、演出报名与结算（T-032~T-034）。

## 9. 风险与取舍

| 风险 | 应对 |
|---|---|
| 客户端改系统时间刷收益 | 无效：上界只用 `serverNow`，与客户端时钟无关 |
| 客户端伪造 `targetAt` 提前推进 | 无效：超上界一律裁剪 |
| 客户端伪造收益 | 不可能：收益只在服务端 `settle` 产生，客户端从不上报 state |
| 离线很久一次补算上千条 | `maxSteps 2000`，超出保持 running，客户端续报；`executed` 只回最近 60 条 |
| 每次到点一次往返 | 请求数 = 行动数（测试态 30 秒一次；生产态 10 分钟一次），另有 15 秒心跳兜底 |
| 离线产出受排程长度决定 | **产品口径即「排多少走多少」**：生产态排 7 天（21 条），离线 3.5 小时走完即停，不做任何额外补算（见 §9.1） |
| 断网时不能推进 | 明确提示「需要联网」——挂机游戏的时间本来就在云端 |
| 旧档带 `sessionId` / `localClock` / `speed` | 读时忽略，不迁移 |

### 9.1 离线挂机的产出：排多少走多少（产品口径）

时间尺度（10 游戏分钟/条）决定离线能走多远。数字按生产态 `timeScale=1`：

| 玩家排程 | 离线可推进时长 |
|---|---|
| 3 天（9 条） | 1.5 小时 |
| 7 天（21 条） | **3.5 小时** |
| 14 天（42 条） | 7 小时 |

**产品所有者 2026-11-04 定：离线挂机就是「排多少走多少」，排程走完即停。**

明确不做：

- 不做「离线按日结算」
- 不做「循环排程」
- 不用默认行动（休息 / 日常）填充空槽

因此本工程的实现基线是：**如实结算、可预期、不做任何额外补算**。排程耗尽就是停点，与体力不足、重点事件同级，不是异常也不是待补的洞。玩家能走多远由他自己排多少决定。

## 10. 与 v3 的差异（v4 为什么改）

| | v3 | v4 |
|---|---|---|
| 倍速 | 1×/2×/4×/8×，`clock.speed` 参与上界计算 | **取消，恒 1×**，`clock.speed` 删除 |
| 上界公式 | `gameAdvance(Δ, speed, ts)` | `gameAdvance(Δ, 1, ts)` |
| `start` | 带 `speed`，running 时改速（需先按旧速结算） | **无参数**，running 时幂等返回 |
| 节奏 | 4 档，玩家可自由加速 | 唯一节奏，只由 `timeScale` 决定 |
| 派单实现面 | 需处理改速时的锚点重算 | **少一个分支、少一个字段、少一处并发风险** |

取消倍速的理由（产品口径）：既然一条行动 10 分钟是设计意图，免费 8× 会把实际体感压到 1.25 分钟/条，等于时间尺度形同虚设；且倍速会让离线结算口径变得含糊（按离开时的倍速算？那就等于免费加速产出）。**恒 1× 让"一个行动 10 分钟"成为唯一真相。**

## 11. 与 v2 的差异（历史留档）

| | v2 | v3（→v4 沿用） |
|---|---|---|
| 谁决定推进到哪一刻 | 服务端取 `now` | **客户端报 `targetAt`，服务端校验** |
| 安全边界 | 无（服务端自算，客户端无从伪造） | **上界公式 + 裁剪 + 整份覆盖** |
| 运行中改状态 | 必须自动暂停（`PUT` 要求 `run.at === gameAt`） | **静默 `advance` 对齐，不暂停** |
| 读路径 | `GET` 会推进并落库 | **`GET` 纯读** |
| 断网 | 只能等 | 客户端知道该报多少，恢复后一次补齐 |
