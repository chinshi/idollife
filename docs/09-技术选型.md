## 0. 技术约束（从需求推导）

| 需求 | 技术含义 |
| --- | --- |
| Web 文字游戏，无美术 | 无资源加载压力，包体不是瓶颈 |
| 随时可中断 | 状态必须可持久化，不能有内存里的关键状态 |
| 时间由**排程**推进 | 不需要真实时间差计算，只需要「行动 → 时间」的映射 |
| 单机为主 | 日常玩法尽量离线可玩；联机与校验才联网 |
| 异步联机、**无榜单** | 不需要实时通信，也不需要服务端权威 |
| 免费 + 赞助 | 部署成本接近 0 |
| 单人开发 | 技术栈要「一个人能维护」 |

## 1. 候选方案

| 方案 | 说明 | 适合 | 代价 |
| --- | --- | --- | --- |
| **A. Vite + TS + React** | 单页应用，纯前端 | 本项目主推 | 需要自己管状态与存档 |
| B. Vite + TS + 原生 DOM | 无框架，手写渲染 | 极致轻量 | 文本多时 DOM 操作繁琐 |
| C. Next.js | 带 SSR | 需要 SEO | 复杂度高，用不上 SSR |
| D. 游戏引擎（Phaser 等） | Canvas 渲染 | 有美术与动效 | 纯文字用不上，排版反而更难 |

## 2. 建议技术栈

| 层 | 选择 | 理由 | 备选 |
| --- | --- | --- | --- |
| 构建 | **Vite** | 启动快、纯静态产物 | — |
| 语言 | **TypeScript（strict）** | 数值与存档结构靠类型兜错 | — |
| UI | **React 18** | 面板/列表/日志多，组件化省事 | Svelte / 原生 |
| 状态 | **Zustand + immer** | 单 store，易于整体快照存档 | Redux Toolkit |
| 样式 | 原生 CSS / CSS Modules | 文字游戏样式量小 | Tailwind |
| 内容数据 | **JSON + Zod 校验** | 文案与逻辑分离，构建期校验 | YAML |
| 存档 | **localStorage + 版本号** | 单机无需后端 | IndexedDB |
| 时间 | **排程驱动 + 可注入时钟** | 可测、可快进，不依赖真实时钟 | — |
| 测试 | **Vitest** + Testing Library | 与 Vite 同生态 | Jest |
| 前端部署 | Cloudflare Pages / Vercel | 免费、全球可用 | GitHub Pages |
| 后端 | **轻后端**（Hono / Workers） | 只做排期、报名、定时结算、账号 | Supabase / 自建 Node |
| 数据库 | **Postgres**（Supabase 或 Neon） | 账号、报名单、演出结果 | D1 / SQLite |
| 定时任务 | **Workers Cron / pg_cron** | 到点结算，不需要常驻进程 | 外部调度 |

## 3. 关键取舍

- **为什么不用游戏引擎**：本项目 99% 是文字排版，Canvas 反而让滚动、选中、无障碍全变难。
- **为什么状态要能整体序列化**：存档 = `store` 的快照，避免「哪些字段要存」的手工遗漏。
- **为什么后端是「轻」的**：联机**没有榜单**，作弊只坑自己，所以不需要服务端权威。后端只负责「排期 + 撮合 + 定时结算 + 下发结果」。
- **为什么不做实时通信**：异步联机 = HTTP 请求 + 定时任务，不需要 WebSocket，也不需要长连接。这是本项目能单人维护的关键。
- **为什么单机优先**：服务器不可用时自动降级为 NPC 演出，玩家无感。

## 4. 后端边界（2026-10-31 修订：服务端校验）

> ⚠️ 本版推翻 v1.0 的「轻后端、不校验」：因为要做**属性校验、防作弊、时间校验与联机公平**，属性必须被服务器验证。

### 4.1 校验分层（不是全权威）

| 层 | 谁计算 | 服务器职责 |
| --- | --- | --- |
| 单机结算 | 客户端 | **事后校验**：时间戳、速率、收益上限 |
| 联机演出 | **服务器** | 全权计算，客户端只报配置 |
| 存档 | 客户端为主 | 存快照 + 事件日志，可重放 |

**为什么不做全权威**：全权威 = 每一步都要联网，断网没法玩，和「上班摸鱼随时断网」直接冲突。所以选「**客户端算、服务器验**」。

### 4.2 时间校验

| 规则 | 说明 |
| --- | --- |
| **校验点** | 只在**行动完成 / 事件触发 / 演出结算**，不做连续校时 |
| 服务器时钟 | 时间的唯一权威来源 |
| **离线重放** | 服务器按 `lastSyncAt` 重放排程，排程耗尽即停 |
| 速率限制 | 每现实分钟最多推进 N 个行动位（防脚本） |
| 单调递增 | 上报时间戳不得倒流 |

> 注意：**快进本身是合法玩法**（排程连续推进），校验的是「不要超过人类操作速度」，不是禁止快进。

### 4.3 防作弊

- **属性增长上限**：单次行动收益不得超过理论上限
- **单日行动上限**
- **异常标记**：降权、隔离联机场次，**不直接封禁**（误伤成本太高）
- **快照对比**：数值跳变过大则要求重放事件日志

### 4.4 联机

- 演出结算在服务器，客户端只提交配置
- NPC 补位、撮合、结果下发均由服务器完成
- 结算为纯函数 + 种子随机，客户端可本地预估，以服务器为准

> 代价：需要账号 + 服务器 + 事件日志表，**联机前的工作量明显上升**。

## 5. 迁移成本

| 如果以后要… | 需要改动 | 难度 |
| --- | --- | --- |
| 加账号与云存档 | 存档层抽接口，加远端实现 | 中 |
| 加多语言 | 文案已抽 key，补语言包 | 低 |
| 改成移动 App | 复用逻辑层，重写 UI 层 | 中高 |
| **加排行榜** | 需要服务端权威 + 反作弊，架构要重做 | **高** |
| 做非文字版（立绘/抽卡） | UI 层重写 + 资源管线 | 高 |

> 注意最后两行：**现在省掉的东西（榜单、权威校验），将来要补是重活**。所以如果哪天想做排名，等于重做一次后端。
