# 《idollife》行动动画：工序判断与成本估算

> 资产代号 `idol_hero_01` ｜ 2026-11-03 ｜ 依据：`packages/core/data/actions.json`（35 条）、[美术规格与预算 v2.4](idollife-美术规格与预算.md)、[28-时间流逝逻辑梳理与诊断](28-时间流逝逻辑梳理与诊断.md)
> 本文回答两个问题：① 能不能先做角色动画、后做装备；② 每个行动 2–5 秒 / 2–3 段随机播放，大概多少钱。
> **v1.1（2026-11-03 22:50）**：已出 [行动动画规划表与表情设计](idollife-行动动画规划表与表情设计.md)（35 条逐条映射 + 24 段规格 + 9 态表情）；§3.2 / §5 成本按该表更新（新增 3 态表情 +1.5、参数映射验收 +0.2、汗滴拆层 +0.3 = 共 +2.0 人日）。

## 0. 结论先给

1. **工序可以倒过来，而且建议倒过来**——动画和装备之间没有依赖。规格 §5 写的「批次顺序不可调换」约束的是「底模 → 部件」，不是「动画 → 装备」，不冲突。
2. **但「先画动画」不等于能跳过分层**：Live2D 动画是打在 `.moc3` 模型的参数时间轴上的，模型来自分层 PSD。真正能提前的是「底模分层 + 绑定」，而这一步只需要 **1 套样本服装**，不需要等 68 件装备全部定稿。B1 红格打歌服三视图正好可以当样本。
3. **成本的数量级取决于一个你还没定的口径**：按字面「35 个行动 × 3 段」= **105 段、约 95 人日**，比整个角色管线（47 人日）还贵一倍，不建议。按「动作族归并」做是 **约 25 人日**，观感几乎一样。
4. **动画几乎不占纹理预算**：motion 是参数曲线 JSON，2–5 秒约 3–8 KB/段，105 段也不到 1MB；吃显存/图集的是装备贴图。所以先做动画不会挤占后做装备的预算——这也是「可以倒过来」最硬的理由。

## 1. 数据前提（估算的地基）

`actions.json` 实际有 **35 条行动**，按 `category` 分四类：

| category | 中文 | 条数 | 例子 |
|---|---|---|---|
| `growth` | 提升属性 | 12 | 唱 K / 跳宅舞 / 自拍小短剧 / 街头卖唱 / 路演演讲 |
| `recover` | 恢复状态 | 9 | 爆睡 / 萨莉亚 / 漂亮饭 / 游乐园 / 卧病在床 |
| `work` | 赚钱 | 8 | 便利店打工 / 女仆咖啡 / 写真模特 / 直播 |
| `performance` | 演出 | 6 | 演出 / 街演 / 商演 / OM 舞台 / 特典会 |

另有 `affectedStats`（vocal / dance / acting / talk）可做更细的动作族归并且不新增字段。

> 1 天 = 3 行动（D-014，`dailySlots=3`）。所以玩家一天最多看 3 次行动动画，一周目下来重复暴露并不高——**这是「随机播放」值得做、但不必做 105 段的依据**。

## 2. 工序判断：可以先做动画吗

### 2.1 可以，但有一个硬前提

| 依赖方向 | 是否成立 | 说明 |
|---|---|---|
| 动画 → 装备贴图 | ❌ 不依赖 | 动画是 25 个参数的曲线；换装走 `setPartOpacityById`（规格 §2.3），装备是静态覆盖层 |
| 动画 → 模型 `.moc3` | ✅ 依赖 | 没有模型就没地方打关键帧 |
| 模型 → 分层 PSD | ✅ 依赖 | 模型由分层图导出（B2 单） |
| 分层 PSD → **全部 68 件装备** | ❌ 不依赖 | 只要 `01_body / 02_face / 2 发型 / 参数表 / 物理组` + **1 套样本服装** 就能出可打帧的模型 |

**硬前提**：25 参数、7 组物理、变形器树（Deformer 树）必须在做动画**之前冻结**。之后新增的每一件装备都必须挂到这棵已冻结的树上——**不新建参数、不改物理组**。否则动画一播，衣服不跟着身体晃，24 段动作全部要重调。

> 这正是规格 §1.5 扩展契约「扩充装备不触碰参数表/物理组」的另一面：现在它反过来成了对后加装备的约束。

### 2.2 推荐工序（把 B2 拆三段）

| 段 | 内容 | 依赖装备全量？ |
|---|---|---|
| **B2a** | 底模分层 + 25 参数 / 7 物理绑定 + **B1 红格打歌服的裙摆分层**（`ParamSkirt` 网格）→ 出 `.moc3` | ❌ 只需 1 套 |
| **B2b** | **行动动画**（本文的成本主体）+ 常驻 idle 动作 | ❌ |
| **B2c** | 其余装备按 §1.5 契约挂到已冻结的变形器树 | ✅ 这时才需要 |

**注意**：`ParamSkirt` 已在参数表里，但裙摆网格要 B1 分层才有——所以 B2a 必须包含 B1 服装，不能只拿 B0 底模。

### 2.3 两个代价，得认

1. **穿帮验收被推迟**：动作做好时只有 1 套服装，验不了「长下摆 / 大饰品在某动作下穿插」。建议 B2a 顺手做 1 件「最坏情况装备」（最长下摆 + 最大头饰）当验收样本，约 **+0.5 人日**，比事后返工 24 段便宜得多。
2. **后加装备的规范变严**：以前装备可以自由分片，现在必须按已冻结的变形器层级挂（规格 §1.5 已有片数结构，执行时多加一条「挂点校验」）。

## 3. 成本估算

### 3.1 单位成本模型（Q 版 2.5 头身 / 25 参数 / 7 物理）

| 项 | 首段（独立设计） | 同族变体（复用骨架与曲线） |
|---|---|---|
| 姿态设计与三段节奏分镜 | 0.3–0.5 人日 | 复用 |
| Cubism 打关键帧（8–14 条参数曲线） | 0.5–0.8 人日 | 0.2–0.3 |
| 物理跟随（马尾 / 裙摆 / 呆毛）+ 表情混合 | 0.2–0.4 人日 | 0.1–0.2 |
| 验收（不穿插 / 10% 缩略可读 / 与 idle 衔接） | 0.2–0.3 人日 | 0.1–0.2 |
| **合计** | **≈ 1.6 人日/段** | **≈ 0.5 人日/段** |

> 对照：规格 §5 现有「3 待机 + 1 过渡 + 6 表情混合 = 5 人日」是**常驻循环动作**，幅度小、无需姿态设计，所以约 1 人日/段。行动动画有起势/主体/收势，单价更高，两个数不矛盾。

### 3.2 三档方案（均含 2–5 秒时长、每段 2–3 个随机变体）

| 方案 | 分组口径 | 段数 | 动作制作 | 程序接入 | **总计** | 评价 |
|---|---|---|---|---|---|---|
| **A 字面全量** | 35 行动 × 3 变体 | 105 | 35×1.6 + 70×0.5 = 91 | 5 | **≈ 96 人日** | ❌ 超过整个角色管线（47 人日）一倍；35 个「唱 K / 街头卖唱 / 专业歌唱指导」做三段几乎一样的动作，纯浪费 |
| A′ 字面全量（2 变体） | 35 × 2 | 70 | 73.5 | 5 | ≈ 79 人日 | ❌ 仍不划算 |
| **B 动作族归并（推荐）** | 8 族 × 3 变体 | 24 | 8×1.6 + 16×0.5 = 20.8 + 表情/汗滴 2.0 | 4 | **≈ 26.8 人日**（v1.1） | ✅ 语义贴合、无重复感 |
| C 按 category 归并 | 4 类 × 3 变体 | 12 | 10.4 | 4 | ≈ 14 人日 | ⚠ 最省，但「便利店打工」和「写真模特」共用一个动作会串味 |

**推荐的 8 个动作族**（按 `affectedStats` + 场景语义，覆盖全部 35 行动）：

| # | 动作族 | 覆盖行动 | 主体动作示意 |
|---|---|---|---|
| 1 | 歌唱系 | vocal-*、街演、演出 | 仰头张嘴、上身微后、马尾上扬 |
| 2 | 舞蹈系 | dance-*、舞室提高班 | 摆臂、重心左右、踮脚 |
| 3 | 表演 / 谈话系 | acting-*、talk-*、漫展主持 | 侧身、手势、点头 |
| 4 | 舞台系 | 演出 / 商演 / OM / 漫展舞台 | 挥手、定点、鞠躬 |
| 5 | 特典 / 接客系 | 特典会、女仆咖啡、写真模特 | 前倾、挥小手、歪头 |
| 6 | 打工系 | 便利店 / 奶茶 / 发传单 / 家教 / 场地杂务 / 直播 | 递物、擦桌、站姿切换 |
| 7 | 进食 / 休息系 | 爆睡、萨莉亚、寿司郎、漂亮饭、钱汤 | 打盹、捧碗、放松肩线 |
| 8 | 外出 / 病弱系 | 游乐园、旅游、去医院、卧病在床 | 蹦跳、挥手 / 蜷缩、捂额（可复用 `idle_tired`） |

### 3.3 用「随机层」把 24 段做出 48+ 段的观感（不额外加钱）

规格 §2.5 已经写死的判断——「固定 8 秒循环，玩家 30 秒就识破是 GIF」——在这里同样成立，但**不必靠多画段数解决**。给每段动画叠三层独立随机扰动：

| 层 | 变量 | 成本 |
|---|---|---|
| 表情层 | 6 表情里按行动情绪随机挑 1（复用已有 `exp_01..06`） | 0 |
| 视线 / 重心层 | `ParamEyeBallX/Y`、`ParamBodyAngleZ` 幅度与相位随机 | 0 |
| 节奏层 | 2.0–5.0s 内随机时长、起势快慢、物理相位（马尾 L/R 差 0.15s） | 0 |
| **调度器** | 按行动 ID 查族 → 从 3 段里随机选、避免连续两次同段、淡入淡出衔接 | **含在 4 人日程序接入里** |

三层组合后，同一族连续三次播放几乎不会重复。**结论：预算花在调度器上，比花在第 25 段动画上划算。**

### 3.4 非人力成本

| 项 | 增量 | 说明 |
|---|---|---|
| 纹理 / 显存 | **≈ 0** | motion 是参数曲线 JSON，3–8 KB/段；105 段 < 1 MB。吃 16MB 图集的是装备贴图 |
| 首包 | +0.2–0.5 MB | 纯数据，不进图集 |
| **道具贴图** | ⚠ 可能破例 | 若动作里画麦克风 / 扫帚 / 碗，每件都是新贴图 + drawable + 图集占用。**建议不画**：2.5 头身小圆手拿不住东西，用姿态暗示即可 |
| 程序接入 | 3–5 人日 | 随机调度、避免连播重复、打断 / 淡出、与行动结算时机对齐 |

## 4. 风险与隐藏成本（三个都得先和程序对）

1. **倍速撞车**：28 文档里 8× 倍速下一条行动约 **3.75 秒**，而动画是 2–5 秒真实秒。若动画按真实秒播且不阻塞，快进时会出现「上一条动画还没播完，下一条已开始」。**建议定义：动画不阻塞行动流程，可被下一条打断并 0.2s 淡出**；这条要写进前端验收。
2. **节奏拖慢**：文字游戏核心是读文本，1 天 3 行动、每次强制播 2–5 秒会拖节奏。建议角色小窗内播放、**可跳过 / 可关闭**（正好复用规格里「老板键 / 灰度模式」的开关位）。
3. **随机种子与服务端重放**：28 文档提到行动结算按 `seed:action:行动id` 派生（D-010）、可被服务端逐字重放。**动画随机建议接同一个 seed**，这样回放一致、也便于复现 bug；否则前端随机与服务端结算各走一套，联调会很痛。

## 5. 与现有预算的关系

规格 §5 的 **47 人日不含本文的行动动画**（那里只有 3 待机 + 1 过渡 + 6 表情混合 = 5 人日）。两套动作共用同一套 25 参数 / 7 物理，**不重复建参数、不重复绑定**。

| 口径 | 人日 |
|---|---|
| 原 L1 管线（B0 底模 + B1 一套服装 + 分层绑定 + 常驻动作） | 47 |
| 行动动画（方案 B，24 段 + 随机层 + 调度器 + 3 态表情） | **+26.8** |
| B2a 最坏情况验收样本 | +0.5 |
| **合计（不含其余 67 件装备）** | **≈ 74.3 人日** |

其余装备按 §1.5 契约逐件加：服装 4–5 人日/件、发型 4–6、发色 1–2、饰品 0.5——**这部分可以无限后推，不受动画影响**。
