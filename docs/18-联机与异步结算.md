# 18 · 联机与异步组团演出

> 状态：🟠 填充中 ｜ 负责人：陈曦 ｜ 更新：2026-10-29
> 上游：[02 核心玩法](02-核心玩法与循环.md) ｜ 关联：[12 时间系统](12-番茄钟与时间系统.md) · [09 技术选型](09-技术选型.md) · [11 存档](11-数据模型与存档.md) · [13 里程碑](13-里程碑与迭代.md)

## 本文回答什么

- 联机到底怎么「联」？玩家什么时候和别人同台？
- 「自选大演出」怎么触发、消耗什么、给什么？
- 为什么它不需要排行榜，也不需要服务端权威？

## 0. 结论

| 维度 | 结论 |
| --- | --- |
| 形态 | **异步组团演出**：不是对战，不是排行榜 |
| 参与 | **玩家自选**——想打就报名，不打不惩罚 |
| 撮合 | 报名池 + 系统撮合 + **NPC 补位**，零沟通 |
| 收益 | 比 NPC 高 **10–25%**（按配置），另有限定掉落 |
| 成本 | 消耗更高（体力 / 资金 / 占用一个周末行动位） |
| 技术 | **轻后端**：排期 + 报名 + 到点结算，无需服务端权威 |
| 定位 | 单机为主；联机是粘性与自发传播的钩子 |

## 1. 为什么是「组团演出」而不是对战或榜单

1. **没有榜单 → 不需要防作弊。** 排行榜才要求属性服务端持有；合作演出里作弊只坑自己。
2. **合作对摸鱼玩家友好。** 不用比、不用赶，只看「这场演得怎么样」。
3. **纯文字战报是天然优势。** 谁发挥失常、谁救了场，文字能写得很具体。

## 2. 与时间系统的关系

- 单机时间由**排程**推进（可暂停、可快进），见 [12](12-番茄钟与时间系统.md)
- 演出按**游戏内日历**开放：每 2 个游戏周开放一个报名窗口
- 到点由服务器统一演算，玩家不需要在场

| 每天推进 | 1 个游戏周 | 报名窗口间隔 |
| --- | --- | --- |
| 16 小时 | 3.5 小时 | 约 **7 小时现实**（3 次/天） |
| 8 小时 | 3.5 小时 | 约 14 小时（1–2 次/天） |

> 因为**参与是自选的**，所以窗口密集不等于负担：玩家只在想打的时候回来看。

## 3. 大演出：自选的高投入高回报

| 项 | 设定 |
| --- | --- |
| 开放频率 | 每 2 个游戏周一个窗口 |
| 参与方式 | 报名（1 次点击）+ 配置（曲目 / 定位 / 道具） |
| 消耗 | 高于日常演出：体力 −30%、资金 −X、占用 1 个周末行动位 |
| 收益 | 日常演出的 **1.1–1.25 倍**（按配置浮动）+ 限定掉落 |
| 风险 | 可能触发负面事件（口碑下滑、受伤），概率低 |
| 缺席 | **不记录为失败**，只损失这次机会 |

三条硬约束：

1. **不打也能通关。** 净收益差控制在 10–25%，不是 2 倍——否则「自选」会变成「必须」。
2. **消耗可再生资源。** 花的是体力、钱、行动位，不是永久属性。
3. **错过不惩罚。** 没报名 = 这周没演出，不是失败、不掉粉、不断连击。

## 4. 报名与撮合（零沟通）

```
点「报名」→ 到点系统撮合报名池 → 人数不足补 NPC → 自动演算 → 出结果
```

- **不邀请**：没有「拉人」这个动作，不用等好友上线
- **不聊天**：没有临时协调
- **不连击**：没有「必须凑满 5 人才开」的门槛

> 这是「轻联机」的关键：玩家只做一个动作——报名。

## 5. 结算输出

| 输出 | 内容 |
| --- | --- |
| 演出评级 | S / A / B …（团队整体） |
| 个人贡献 | 你在整场里的占比与评价 |
| 战报 | 3–8 句文字：谁发挥好、哪里出了意外 |
| 奖励 | 资金、道具、限定掉落 |

**团队评级决定演出成不成功，个人贡献决定你拿多少**——这样配置才有意义，混子拿不到全额。

## 6. 属性修正

玩家进度不同，同台需要拉平：

- **只修正评分，不修正收益。** 评分归一化保证公平；收益仍按自己属性算，老玩家不会觉得白练
- **基准用场次档位**（如「本场按 T2 档计算」），不用队伍平均——可预期，不会被队友拖累

## 7. 技术方案

| 能力 | 单机模式 | 联机模式 |
| --- | --- | --- |
| 演出结算 | 本地跑（NPC 队友） | 服务端跑（真人队友） |
| 报名 / 撮合 | 不需要 | 服务端 |
| 定时开演 | 本地日历 | 服务端定时任务 |
| 数据一致性 | 本地存档 | 提交单上传、结果下发 |

- 两端跑**同一份结算函数**（纯函数 + 种子随机），保证结果一致
- **服务器不可用时自动降级为 NPC 演出**，玩家无感、不惩罚
- 因为无榜单，不需要服务端权威校验属性——只需基础校验（次数上限、时间戳）

## 8. 数据结构草案

```ts
/** 一个演出窗口 */
interface ShowWindow {
  id: string;
  gameWeek: number;      // 对应游戏内第几周
  openAt: number;
  lockAt: number;
  settleAt: number;
  ruleVersion: string;
}

/** 报名单 */
interface Entry {
  windowId: string;
  playerId: string;
  role: 'main' | 'sub' | 'dance';
  songId: string;
  items: string[];
  submittedAt: string;
}

/** 结算结果 */
interface ShowResult {
  windowId: string;
  playerId: string;
  grade: 'S' | 'A' | 'B' | 'C';
  contribution: number;   // 0–1
  report: string[];
  rewards: { money?: number; items?: string[] };
  seed: string;
}
```

## 9. MVP 边界

联机**不进 MVP**。但 MVP 要留两个口子：

- [ ] 演出结算写成纯函数，能传入 `seed` 与队友列表（NPC 也是队友）
- [ ] 队伍成员抽象成数组，不是写死的单人

## 10. 风险

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| 冷启动没人 | 全是 NPC，体验等于单机 | NPC 演出本身要好玩；不把联机当唯一卖点 |
| 收益差过大 | 「自选」变成「必须」 | 净收益差锁在 10–25% |
| 搭便车 | 混子拿全额 | 贡献度拆分奖励 |
| 服务器故障 | 演出无法结算 | 自动降级 NPC，结果照发 |
