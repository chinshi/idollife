## 2. 任务系统

### 2.1 配置表 `data/tasks.json`

| 字段 | 含义 | 取值 |
| --- | --- | --- |
| `id` | 任务 id（唯一） | 字符串 |
| `type` | 任务类型 | `once` 一次性 / `repeat` 长期 |
| `name` | 任务名 | 中文 |
| `displayCondition` | 可见条件（不满足则不出现） | 条件 DSL |
| `acceptCondition` | 可领取条件（满足才能领取） | 条件 DSL |
| `completeCondition` | 完成条件（领取后满足即自动完成并发奖） | 条件 DSL |
| `rewards` | 奖励 | `money` / `stamina` / `fans` / `stats` |
| `times` | 可执行次数 | 数字，0 = 无限制 |
| `content` | 任务内容（详情说明） | 文本 |
| `brief` | 任务简报（一句话，显示在信息区） | 文本 |
| `priority` | 优先级 | 数字，**越小越靠前** |

示例：

```jsonc
{
  "id": "task-first-show",
  "type": "repeat",
  "name": "站上舞台",
  "displayCondition": { "statsSumAtLeast": 60 },
  "claimCondition": { "fansAtLeast": { "stage": 100 } },
  "rewards": { "money": 800 },
  "times": 5,
  "content": "演出会把路人变成粉丝。",
  "brief": "舞台粉累计到 100",
  "priority": 30
}
```

### 2.2 条件 DSL（推荐用[表达式](26-条件表达式.md)）

沿用事件系统，任务额外支持：

| 字段 | 含义 |
| --- | --- |
| `statsBelow` | 单项属性**低于** | `{ "dance": 50 }` |
| `moneyAtLeast` | 资金不少于 |
| `friendsAtLeast` | 朋友圈人数不少于 |
| `flagsContain` | 这些标记都存在（如 `ev:debut`） |

其余可用：`statsAtLeast` / `axesAtLeast` / `axesBelow` / `staminaBelow` / `statsSumAtLeast` / `statsSumBelow` / `fansAtLeast` / `flagsNot`。

### 2.3 领取与次数

- 领取次数记在存档标记里：`task:<id>:claimed = 次数`
- `type: once` 的任务领过一次后不再可领
- `times` 为 0 表示**不限制次数**（每次满足条件都能领）
- 领奖会写日志：`完成任务「xxx」。（+¥800 · 粉丝 +100）`


### 2.3 任务状态机

```
未达可见条件 → 可见但不足可领取条件 → 可领取 → 进行中 → 已完成
```

| 状态 | 条件 | 界面 |
| --- | --- | --- |
| `hidden` | 不满足 `displayCondition` | 不显示 |
| `locked` | 可见但未满足 `acceptCondition` | 显示「未达成」 |
| `claimable` | 满足 `acceptCondition`、未领取 | 显示「领取」按钮 |
| `active` | 已领取、未满足 `completeCondition` | 显示「进行中」 |
| `done` | 已领取且满足 `completeCondition` | 移入「已完成」页签 |

- 完成时**自动发奖**（不需要再点领取），并写日志
- 已完成任务按**完成时间倒序**排列在「已完成」页签
- 任务页签分为 **领取任务 / 已完成**
- 菜单「任务」右侧会显示**可领取数量**角标
- 任务简报只显示**进行中**的任务，按领取时间从早到晚
### 2.4 界面

| 位置 | 展示 |
| --- | --- |
| ③信息区 | 最多 6 条**任务简报**，按 `priority` 排序，可领取的变橙加粗 |
| ⑤主系统 · 任务 | 完整列表：名称、类型、剩余次数、简报、内容、奖励、领取按钮 |
| ④菜单栏 | 「任务」菜单项（第一行） |

**时限的展示（2026-11-02 补，[T-010](../collab/T-010-任务倒计时UI.md)）**——数值定了但玩家看不见等于没定，所以两处都要给：

| 时机 | 位置 | 文案 |
| --- | --- | --- |
| **领取前** | 任务行的「任务要求」之后 | `时限 3 天`（无限期整项不显示，不写「无限期」占位） |
| **进行中**（`active`） | 状态标签之后 | `剩 7 次行动 · 约 3 天`；剩余 ≤ 1 游戏日时降为 `剩 2 次行动` 并转橙加粗 |
| **到点同刻**（`at === deadlineAt`） | 同上 | `期限已到`（橙）——状态仍是 `active`（判定用 `>`），但要让玩家知道这一步结算就会判超时 |
| **已错过**（`expired`） | 同上 | `明日起重新可领`（中性灰）。**不用红色**：红色是警告色，用在既成事实上只会制造焦虑，也会跟「期限已到」抢注意力 |
| **错过次数** | 任务行的「时限」之后 | `错过 2 次`（累计，仅 `expiredCount > 0` 时显示） |
| **分区标题** | 「全部」页签 | `已错过 · 今日 1 单`（当天错过条数；为 0 时只写「已错过」） |

口径：
- **主单位是「行动」不是「天」**。玩家真正消耗的资源是行动，天只是换算（1 天 = 3 行动）；写成「约 2 天」是因为玩家按天理解节奏。
- 剩余次数**向上取整**：剩 1 毫秒也算「剩 1 次行动」，不允许出现「剩 0 次行动却还在进行中」。
- `completable`（条件已达成等领奖）**不显示倒计时**：`statusOf()` 里 `completable` 判定先于 `pastDeadline()`，达成后不会再过期，奖励是安全的，催反而误导。
- 文案按**状态**分叉而不是按「是否到点」分叉，否则 `at === deadlineAt` 那一瞬会出现「进行中 + 已超时」的自相矛盾行。
- **失败必须可见**（T-011 的教训）：`expired` 当天**不能**用 `hidden`。T-007 拿 `hidden` 做「同日冷却」，结果 `expired` 变成一帧状态——结算立刻把它藏起来，玩家看到的是任务**凭空消失**，面板的「已过期」分区永远是空的，连红色警告都没机会显示。冷却的语义应该是「**不可操作**」而不是「**不可见**」。
- 错过是**软失败**：目的不是罚玩家，是让他知道「这班车没赶上、明天还有」。所以文案用「明日起重新可领」而不是「失败」，色调用灰而不是红。

### 2.5 时限、重置、任务链、进度（S04 收尾规格）

> 本节对应 §4 待办的 4 条，是 S04「通告与工作」从"能用"到"完整"的收尾。字段全部可选，缺省即保持现有行为——**不破坏已有 24 条任务**。

#### A. 过期时间 `deadlineDays`

> **单位说明（2026-11-02 修订，[D-014](16-决策记录.md)）**：1 行动 = 10 游戏分钟，一天 = 3 行动 = 30 游戏分钟。
> 原设计用「游戏小时」，在这个尺度下 1 游戏小时 = 2 游戏日，导致「短通告 12 小时」= 24 游戏日，明显不合理。
> 因此**改用「游戏日」为单位**，字段名 `deadlineDays`，表头「时限(天)」。

| 项 | 规则 |
| --- | --- |
| 字段 | `deadlineDays: number`（游戏日）；`0` 或缺省 = 无限期 |
| 触发 | 仅 `active` 且 `deadlineDays > 0` 时检查：`now - acceptedAt > deadlineDays × DAY_MS` |
| 状态 | `expired`（在 `active` 之后）：**当天可见但不可操作** |
| 名额 | 过期**不消耗 `times`**（机会还给玩家） |
| 日志 | 「通告「xxx」超时未完成。」**每次超时只写一条**（同日内重复结算不得重复写） |
| 冷却 | 记 `task:<id>:expiredDay = 当前游戏日`；当天任务**留在面板上**显示「已错过」，次日恢复可领（[T-011](../collab/T-011-失败可见化.md)） |
| 记录 | 记 `task:<id>:expiredCount` 累计错过次数，**只展示不产生数值后果**（面板「错过 N 次」） |
| 惩罚 | **不做**。第一版软失败：不扣钱、不扣粉、不掉心情、不消耗次数。信誉系统落地后再谈后果 |

首批数值（按通告体量分级，后续由内容侧调整）：

| 类型 | `deadlineDays` | 折算行动数 | 适用 |
| --- | --- | --- | --- |
| 短通告 | 1 | 3 行动 | 单次打工、录音 |
| 普通 | 3 | 9 行动 | 演出、拍摄 |
| 长期 | 7 | 21 行动 | 系列任务、组合任务 |
| 无限期 | 0 | — | 现有 21 条 `once` 型成长任务全部保持 0 |

> 判据：玩家一天只有 3 个行动，「3 行动内做完」是紧迫但不强人所难的下限；7 天（21 行动）是长期任务的体感上限，再长就没有「通告」的紧迫感了。

##### 首批数值 v1（2026-11-02，试玩版，可调）

> 已写入 `content/all.xlsx` 的 tasks 表第 15 列，导入后 `tasks.json` 生效。备份 `content/_all-backup-before-deadline-values.xlsx`。

| 时限 | 条数 | 任务 | 判据 |
| --- | --- | --- | --- |
| **1 天**（3 行动） | 2 | `task-first-show` 站上舞台、`task-daily-repeat` 每日一练 | 当天的活当天结，配合 `reset=daily` 形成日节奏 |
| **3 天**（9 行动） | 6 | `task-vocal-20` / `task-dance-20` / `task-acting-20` / `task-talk-20`、`task-friend`、`task-show-10` | 单属性推到 20 的量级，9 个行动够但不宽裕 |
| **5 天**（15 行动） | 4 | `task-dance-30`、`task-total-200`、`task-fans-300`、`task-party-5` | 需要组合动作（练 + 演出 / 社交）才够 |
| **7 天**（21 行动） | 3 | `task-total-300`、`task-fans-1000`、`task-money-10000` | 一周尺度的中期目标，超过就没紧迫感 |
| **无限期**（留空） | 9 | `task-first-debut`、`task-debut-party`、`task-first-cheki`、`task-manager-push`、`task-first-om`、`task-burnout`、`task-fan-letter`、`task-first-audition`、`task-money-50000` | 前 8 条是**剧情旗标**（等事件触发，催不得）；`money-50000` 是长线积累（按当前 faucet 需 40+ 天，给任何期限都只是折磨） |

**设计口径**：时限表达的是「这张单的有效窗口」，不是惩罚。过期不扣钱、不扣粉、不扣信誉、不消耗 `times`，次一游戏日重新可领（T-007）。所以即便时限偏紧，代价也只是「今天没赶上这班车」。

⚠️ **已知缺口**：这 24 条里**没有真正的「限时接活」通告**（打工 / 录音 / 拍摄 / 街宣这类一次性、有替代、错过不致命的活）。现有内容全是成长里程碑与剧情旗标，时限系统只在 3 条 repeat 任务上真正跑起来。要让时限成为玩法而不是压力，需要**新增一批通告型任务**（见 docs/04 待填的经济与通告部分）。

#### B. 重置周期 `reset`

| 取值 | 行为 |
| --- | --- |
| **缺省（不填）** | **按 `type` 推断**：`once` → 永久完成；`repeat` → `daily`（即 D-011 现有行为） |
| `none` | `times` 用尽即永久 `done`（**显式关闭跨日重置**） |
| `daily` | 每游戏日重置领取次数 |
| `weekly` | 每 7 游戏日重置 |

> **缺省 ≠ `none`**：缺省是"维持 D-011 现状"，`none` 是"明确关闭"。这样加字段不会改变现有 24 条任务的任何行为。写成 `none` 才会让 repeat 任务变成"完成一次即永久 done"。

#### C. 任务链 `prerequisite`

- 字段：`prerequisite: string[]`，缺省空 = 无前置
- 前置任务未全部 `done` → 本任务状态 `hidden`（不可见，不是 `locked`）
- `check:data` 必须校验：① id 存在；② 不得自引用；③ 不得成环（拓扑检测）

#### D. 进度条

- 解析来源：`completeCondition`，**仅在形如 `<变量> >= <数字>` 或 `<变量> > <数字>` 时提供进度**；复合表达式（含 `and` / `or` / 函数）不提供，优雅降级为纯文字
- 当前值必须复用表达式变量表（`expr.ts` 构造 `data` 的那段），**不得另写一套取值逻辑**
- UI：`舞蹈 18/30` + 进度条；`> n` 的目标值按 `n + 1` 展示

#### E. 本节引入的待确认

**一个行动推进多久，两处口径冲突**，需先拍板（已登记 docs/17）：
- docs/12 §2 表：生存期「一个行动推进 **1 游戏日**」
- docs/12 §3 + `balance.actionMinutes`：**1 行动 = 10 游戏分钟**

本节 `deadlineDays` 以**游戏时钟**（`state.at`）为准，换算用 `DAY_MS`。口径已于 2026-11-02 定案（[D-014](16-决策记录.md)：1 行动 = 10 游戏分钟、一天 = 3 行动 = 30 游戏分钟），**不再是待定项**；单位随定案由「小时」改为「游戏日」（[T-009](../collab/T-009-时限单位改为游戏日.md)）。
